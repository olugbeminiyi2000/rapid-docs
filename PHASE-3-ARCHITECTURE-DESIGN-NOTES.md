# rapid-docs — Phase 3 Architecture Design Notes

Purpose of this document: same as the Phase 1 & 2 notes — a record of *why*, not just *what*. This one covers Objective 3.1 (the NestJS foundation) and the Objective 3.2 architecture pivot, including the reasoning that led to dropping several originally-planned technologies from the tool itself.

---

## Objective 3.1 — The NestJS Foundation

### 1. Why NestJS over plain Express/Fastify
**Reasoning:** plain Express is unopinionated — every codebase organizes itself differently, and nothing enforces structure as it grows. NestJS enforces a specific shape (Modules, Controllers, Providers, wired by Dependency Injection) and has official, built-in support for exactly what later roadmap phases needed (message queues, GraphQL, WebSockets) — though, as this document goes on to explain, most of those later phases were ultimately dropped from this project.
**Correction made along the way:** NestJS's architecture isn't inspired by backend MVC at all — it's borrowed directly from Angular's frontend architecture (Components/Services/Modules). That's *why* it has no built-in Model/ORM layer — Angular, being frontend, never needed one. The absence isn't a gap, it's inherited lineage.

### 2. Understanding decorators to the actual mechanism, not just the syntax
**Approach:** rather than accepting `@Module({...})` as syntax to memorize, traced the real two-step mechanism with a live compiled-output demo: the outer call (`Module({...})`) runs immediately and returns a function; the *returned* function is what the language's decorator machinery calls automatically, passing the class. Proved this by compiling a toy decorator and reading the generated `__decorate` glue code directly, rather than asserting it.
**Extended to prove the deeper mechanism:** dependency injection itself was proven the same way — showed that `emitDecoratorMetadata` causes the compiler to silently emit a `design:paramtypes` array (the *actual* class references, not just type names) onto any class with at least one decorator present, and that Nest's DI container reads this auto-generated metadata to know what to construct and inject. Confirmed the same real distinction elsewhere: `@Module`'s config object is metadata attached to the class as an identity peg; it does not (and does not need to) inspect the class body at all.

### 3. Two real tooling incompatibilities found and root-caused, not worked around
**`tsx` (esbuild) silently breaks NestJS's DI:** esbuild strips types fast without resolving them, so it never emits real `design:paramtypes` metadata. Diagnosed by reproducing the exact same failure in an isolated experiment (`Reflect.getMetadata` returning `undefined` under `tsx`, then succeeding when compiled with real `tsc`) before touching the actual app. Fixed by moving off `tsx` for running the Nest app entirely, and setting up the real `@nestjs/cli` workflow instead.
**TypeScript 7.0 doesn't expose the programmatic compiler API `@nestjs/cli` needs:** found via the CLI's own explicit error message; fixed by pinning to TypeScript 6.x rather than fighting a genuinely incompatible bleeding-edge version.
**Also found (not a Jest problem, a leftover-artifact problem):** stale compiled `.js` files sitting next to their `.ts` sources in `src/`, from an earlier build that ran before `rootDir`/`outDir` were configured. These were silently shadowing the real source files during Jest's module resolution — found and removed, not patched around.

### 4. Migrating the Phase 1/2 engine: move, don't wrap
**The decision:** port the actual logic into real NestJS services (`AstService`, `DocumentationService`), retiring the standalone scripts — rather than leaving `ast-engine/` in place and having services thinly wrap it. Reasoning: Phase 3's own stated goal was moving working scripts into a professional architecture, not gluing old scripts onto a new framework via cross-directory imports.
**Verification, not assumption:** every migrated method was checked against the exact real numbers already proven in Phase 1/2 (20 nodes, the 45-node shorthand-dedup case, the 7-hash rename propagation, the 8-of-16 partial-staleness split, the 12-node undocumented count) via permanent Jest tests — 17 total, all passing, none of them new claims, all of them re-proofs.
**Reversible archiving, not deletion:** since this isn't a git repo, `rm` here is genuinely permanent, not recoverable-trash. `ast-engine/` was renamed to `ast-engine.archived/` rather than deleted, once every real piece of logic (12 files' worth) was confirmed migrated and nothing was found missing.

## Objective 3.2 — The Architecture Pivot

### 5. The MySQL/MongoDB split, as originally reasoned
**Initial design:** MySQL for relational, ownership-shaped data (Users, Repos — fixed columns, foreign keys, JOIN-friendly); MongoDB for the documentation records themselves, since a `DocRecord` (`{docText, members: [...]}`) is naturally nested, variable-length data that would otherwise need an awkward separate `members` table and a join just to reconstruct one record.

### 6. The real problem this exposed: where does the code actually live?
**The tension named directly:** the actual source code being documented lives on the user's local machine; a web app with a remote database does not have direct access to that. This is the same "position isn't identity" lesson from Phase 1, resurfacing one layer up — a repo's *path* isn't a stable identity either, and renames/deletions happening outside the tool (via OS, terminal, or git itself) are invisible to a system that only watches its own explicit rename function.

### 7. GitHub integration — considered, then deliberately rejected
**Why it was tempting:** GitHub's API would give a remote server direct, reachable access to a repo's file content and history, without needing anything running locally.
**Why it was rejected:** it conflates "git" (the tool, which works entirely locally with zero dependency on any hosting service) with "GitHub" (one company's hosted product on top of git). Depending on GitHub specifically means OAuth complexity, API rate limits, webhook reliability, and a hard requirement that every tracked repo be hosted there — none of which are actually required to get git's real capabilities (diffing, content-based rename detection).
**Kept from the GitHub discussion:** the *idea* of syncing an access list from an external source via webhook rather than duplicating it by hand — just recognized this only matters if we ever integrate with a hosting platform at all, which the final direction doesn't require.

### 8. Thin local agent + remote server — considered, then rejected in favor of a full desktop app
**Why it was tempting:** decouples from GitHub while still keeping a central, multi-user server.
**Why it was rejected, given the explicit priority (least complexity, most effective, fewest bugs):** an agent-plus-server design is a genuine distributed system — two processes on two machines, communicating over a network — and inherits a whole category of failure modes that simply cannot exist in a single local process: network timeouts, partial uploads, retry-induced duplicate processing, auth-token expiry between agent and server, version drift between the two sides. A full desktop app eliminates all of these *by construction*, not by careful engineering around them — a structurally stronger correctness guarantee than anything that could be built carefully on top of a network boundary.
**What this preserves for free:** full access to the live, uncommitted working directory, not just what's been pushed somewhere — resolving a scope question (pushed-only vs. local-including-uncommitted) that the GitHub-API approach would have forced a compromise on.

### 9. IPC, not HTTP — the actual mechanism inside the chosen design
**Clarified precisely, not just asserted:** an Electron app is two processes on the same machine (a Node.js main process with full system access, and a sandboxed Chromium renderer process for the UI) — genuinely separate, so *some* communication is still required between them. The point was never "no communication," but that Electron's own IPC mechanism is sufficient, because it never needs to solve the problems HTTP exists for (unreliable delivery, latency, encryption over a public network) — those problems only exist when crossing a real network boundary between different machines, not a process boundary on the same one.
**What carries over unmodified:** `NestFactory.createApplicationContext()` builds the exact same DI-wired services with zero HTTP server involved; the main process calls `docService.checkFile(...)` as a plain, direct, in-memory function call. Nothing about `AstService`/`DocumentationService`'s own code needs to change — only the "front door" changes, from `@Controller()`/HTTP routing to an IPC handler.

### 10. Documentation collaboration: git's real branches, not a custom parallel system
**The instinct:** each collaborator should work in isolation (their own "branch") rather than editing one shared, live copy directly, mirroring how git itself avoids direct pushes to a protected `main`.
**The resolution:** rather than inventing a custom branch-like concept for our own documentation metadata, store documentation records as real, git-tracked files inside the repo (e.g. a `.rapid-docs/` folder). Doing this means every one of git's existing collaboration mechanisms — branches, pull requests, branch-protection rules, merge-conflict detection — applies to documentation automatically, for free, with zero custom code, because from git's perspective they're just files like any other. This directly resolves the "someone might push straight to `main`" worry: whatever protection rule already exists for the code also covers the documentation, since it's subject to the same rules.
**Same principle as Phase 1/2's hash function decision:** reuse a proven, battle-tested mechanism (git's merge/conflict/protection machinery) instead of rebuilding a parallel version of it ourselves.

### 11. The final scope decision, and why
**Kept:** TypeScript, Jest, NestJS (as the DI/service structure, minus the HTTP layer), Electron, and the entire Phase 1/2 engine — unaffected by any of this, since it's pure logic that doesn't care where it runs.
**Dropped from this tool specifically:** MySQL, MongoDB, RabbitMQ, GraphQL/WebSockets, GitHub-platform integration. Each of these was originally justified by a *multi-user, always-on, remote-server* concern (shared-server overload, centralized ownership records, pushing live updates to a remote dashboard) that mostly stops applying once the tool is local-first and single-user by design.
**Why "dropped" rather than "failed to use":** forcing a technology into a project because it was originally planned, after the project's actual shape has genuinely changed, would be the same mistake as over-engineering for a hypothetical requirement — something this whole build has consistently avoided. The right move is matching tools to real, current needs, not sunk-cost loyalty to an earlier plan.
**Explicitly not wasted, just relocated:** MySQL/MongoDB remain genuinely worth learning — just not by force-fitting them here. A separate, appropriately-scoped project (e.g., a bug-reporting/telemetry system for this tool, which *is* naturally centralized, shared, and server-hosted) is a more honest place to use them.
**A real, underlying cost/accessibility reason, not just architectural taste:** requiring users to host and pay for database infrastructure just to use a local tool creates a real barrier to who can actually use it. Going local-first removes that barrier entirely — a concrete, practical justification alongside the correctness/complexity reasoning above.

## Objective 3.3 — The Electron Shell: First Boot

### 12. The goal, kept deliberately minimal
**The task:** get a bare Electron window to open and render a static string ("rapid-docs desktop shell — it's alive") — no NestJS, no IPC, nothing wired in yet. The point was to isolate Electron's own startup mechanics from every other moving part, so that if something broke, there would only be one place to look.

### 13. First real bug: ESM named imports against a CJS module
**Symptom:** `SyntaxError: The requested module 'electron' does not provide an export named 'BrowserWindow'`.
**Why:** `import { app, BrowserWindow } from "electron"` is a named-import, which requires the target module to actually be ESM (or for a tool to statically analyze a CJS module's `module.exports` shape ahead of time). Electron's package is CommonJS, so Node's native ESM loader can't see named exports on it.
**Fix:** default-import the whole module object, then destructure at runtime — `import electron from "electron"; const { app, BrowserWindow } = electron;`. This works under both ESM and CJS because it never asks the loader to statically resolve named exports.

### 14. Second real bug: `app`/`BrowserWindow` were `undefined` even after the import was fixed
**Symptom:** `TypeError: Cannot read properties of undefined (reading 'whenReady')` — the import no longer threw, but the destructured values were empty.
**First wrong lead, ruled out by reading source directly rather than guessing:** read `node_modules/electron/index.js` itself. It turned out to just be a small shim:
```javascript
module.exports = getElectronPath(); // returns a STRING path to electron.exe
```
This is the version of the `electron` npm package meant for *external* tooling — e.g. Playwright's `_electron.launch()`, or the `electron` CLI itself — to locate the real binary so they can spawn it as a subprocess. It is deliberately not the real `app`/`BrowserWindow` API. This explained *what* we were getting, but not yet *why* our own main process — which should be running *inside* the real Electron binary — was resolving to this external shim instead of Electron's real, internally-injected module.
**Two more contributing issues found and fixed on the way (real, but not yet the root cause):**
- **CommonJS vs. ESM for the Electron main process specifically:** Electron's special interception of `require("electron")` (the mechanism that swaps in the real API) hooks into Node's CommonJS `require`, not the newer ESM `import`. The rest of the project is ESM (`"type": "module"` in the root `package.json`), but the Electron main process doesn't need to match that — it's an isolated entry point. Fixed by giving `electron/tsconfig.json` its own `module: "CommonJS"` compile target.
- **Node's directory-scoped module-type detection:** once compiled to CommonJS, Node still refused to run the output (`ReferenceError: exports is not defined in ES module scope`), because Node determines a plain `.js` file's module system by walking up to the nearest `package.json` — and the root one says `"type": "module"`, which applies to the whole tree by default. Fixed by adding a scoped `electron/package.json` with `"type": "commonjs"`, overriding just that subtree.
**The actual root cause, found only after building a minimal, isolated probe script** (`console.log(process.type, require("electron"))`, nothing else) and running it directly against the raw `electron.exe` binary (bypassing `npx` entirely, to remove one more variable): `process.type` printed `undefined` instead of Electron's expected `"browser"` for a real main process. Checking the shell environment directly (`env | grep -i electron`) found `ELECTRON_RUN_AS_NODE=1` already set. This is a real, documented Electron flag — VS Code's own extension host uses it, since VS Code is itself an Electron app that needs to spawn plain-Node subprocesses using the same bundled binary rather than shipping a second Node install. With that flag set, `electron.exe` skips its entire normal app-launch path and behaves as a generic Node runtime — which is exactly why `require("electron")` was giving the external path-string shim instead of the real API: from Electron's own perspective, this never was the main process to begin with.
**Fix:** unset `ELECTRON_RUN_AS_NODE` for the launch command specifically (not globally, since something in this environment may depend on it being set elsewhere). Re-running the same probe then showed `process.type: "browser"` and the full real API (`app`, `BrowserWindow`, `ipcMain`, and everything else).

### 15. Verified by looking, not by assuming the fix worked
**Discipline applied:** rather than treating "no error thrown" as success, drove the compiled app with Playwright's `_electron`, extracted the rendered page text (`"rapid-docs desktop shell — it's alive"` — an exact match, not an approximation), took a real screenshot, and visually inspected the image before calling the objective done.
**Temporary artifacts removed once verification was complete:** the Playwright driver script, the screenshot, a manual test log, and the minimal probe script — none of which are part of the actual app.

## Objective 3.4 — GitService: Design and Implementation

### 16. Git fundamentals proven with real repos before any design was attempted
**The discipline:** rather than assuming how git's three-state model (working tree / index / HEAD) or `pull` actually behaves under every combination of local edit state, every claim was tested against real, disposable git repositories — plain edits, `git add`, `git commit`, then `pull` against a second real clone acting as a collaborator.
**What this proved, concretely:** the working tree is not something git manages at all (just live disk state); the index and HEAD only advance on explicit commands; `pull` never silently overwrites uncommitted or staged work (it refuses outright, naming the exact files); a real merge only happens once *both* sides have diverged with actual commits, producing a genuine two-parent merge commit; and conflicts are resolved at the *line* level, not the whole-file level — two commits changing different lines of the same file merge automatically no matter how different the resulting file looks overall.

### 17. Why GitService is structurally stuck with the "hard" comparison
**The finding:** our tool only ever observes two finished commits — the last one it processed, and current HEAD after however many pulls happened in between. It never gets the easier, index-mediated, step-by-step view the original author had while making the change. That's the comparison that most readily loses a rename (a direct jump from old HEAD to new HEAD, skipping the index entirely), and there's no way to substitute an easier comparison — it's the shape of the problem, not a design choice.
**Efficiency concern raised and resolved:** worried that comparing across many skipped commits accumulates work — disproven directly by committing three changes to the same file (add, edit, delete) between two pulls and showing the direct two-point diff comes back completely empty, since the net effect collapses automatically. Cost is proportional to actual net change, not to how many commits were skipped.
**`ORIG_HEAD` tested and rejected as a free substitute:** git does keep one automatic "before this merge" pointer, but a second, unwitnessed pull was shown to overwrite it — it only ever remembers one pull back, not an arbitrary gap since our tool last looked. Confirmed our own persistent pointer is unavoidable, not a redundant precaution.

### 18. The rename similarity threshold: chosen lenient, and its real limit found by testing, not assumed
**The choice:** lenient (`1%`), reasoned from asymmetric failure cost — a false-positive rename gets caught loudly by `checkFile`'s existing drift detection once run against the wrongly-matched content, while a missed rename silently orphans a `DocRecord` with nothing pointing to it.
**A real, hard floor found underneath that choice:** if a rewrite shares *zero* literal lines with the original, similarity comes back as a true, hard 0% — proven directly, including at the absolute floor `-M0%`. No threshold can manufacture a similarity signal that isn't there.
**Proven to be mechanism-independent, not a `git mv` quirk:** committed the identical end state three ways — `git mv` + rewrite, manual `rm` + create, and plain OS-level `mv` + `git add -A` — all three produced byte-identical tree objects. Git's commit model has no concept of "rename" stored anywhere; every rename judgment is a post-hoc content comparison, regardless of which tool performed the actual change.
**Initial framing of the consequence corrected:** first described as "silent, permanent data loss." That was too strong — once a deletion handler exists that *surfaces* what it removes (rather than silently discarding it), an undetected rename just degrades to two separately-visible events (an old record flagged as gone, a new file flagged as undocumented) instead of one connected one. The real cost is lost auto-continuity (the old prose doesn't carry forward automatically), not silent breakage — and that softer framing is itself conditional on the deletion handler being built to report, which it wasn't yet at time of writing.

### 19. Where the "last synced commit" pointer lives — a real bug caught before it shipped
**Initial design (wrong):** stored inside `.rapid-docs/`, the same git-tracked folder as the shared documentation records.
**Why that's a real bug, not a style nitpick:** the pointer is per-machine, per-installation sync progress — "what *this* tool instance has processed" — not shared content. If tracked and pushed, one collaborator's own sync progress would silently overwrite another's on pull, causing a tool instance to believe it's caught up on commits it never actually processed. Exactly the class of silent failure this whole design effort was meant to avoid.
**Fix, proven correct rather than assumed:** moved to `.git/rapid-docs/last-sync.json`. Directly tested that `git add` on a path inside `.git/` is a silent no-op — `git ls-files` and `git status` confirm it never enters the index. This is a structural guarantee from git itself, not a convention that could be violated by accident.
**Ownership decided in `GitService`'s favor, correcting an earlier lean:** originally assumed `GitService` should mirror `AstService`'s statelessness, with `DocumentationService` (which already owns `storage/`) holding the pointer instead. Reversed on reflection: unlike parsing/hashing, "what changed since I last looked" *inherently* requires memory — that's not an artificial state being bolted on. And the pointer is git-domain data (a commit hash), not documentation-domain data; keeping it in `GitService` means `DocumentationService` never needs to know what a commit even is.

### 20. Modified vs. renamed: clarified as two orthogonal questions, not two points on one scale
**The distinction:** "modified" answers *did the content change* (same path, before and after); "renamed" answers *did the identity change* (different path, with content similarity above the chosen threshold — anywhere from 0% actual change up to just-under-threshold). A rename is not "a rename with no content change" — it can carry any amount of drift right up to the threshold.
**Why this directly justifies the chaining rule:** `renameFile` alone only fixes identity (moves the record to the new path); it says nothing about whether the content is still accurate. Since a renamed file can just as easily have drifted content as a merely-modified one, every renamed entry must chain into `checkFile` immediately afterward — not deferred to whenever the file might next be opened live, since a collaborator's rename might never be touched by the local user at all.

### 21. The deletion handler: design settled, not yet built
**The decision:** when a file disappears entirely, surface a message exposing the record's original `docText` (so the human can read or copy anything still relevant), then actually delete the record — reasoned directly: leaving an orphaned record pointing at nothing forever isn't useful once nothing in the repository could ever reference it again.
**A related distinction drawn precisely:** if a human manually copies old text into a fresh `writeDoc` call for whatever replaced the deleted file, that is *not* the renaming mechanism reactivating — it creates a brand-new `DocRecord` with freshly computed hashes against the new file's actual nodes. Same convenient outcome for the human, entirely different, unconnected mechanism under the hood.

### 22. Implementation, tested against real repos throughout — and two bugs the tests themselves caught
**Shape:** `GitService.diff(repoPath, from, to)` parses real `git diff --raw -M1%` output into `{added, deleted, modified, renamed}`; `getHeadCommit`/`getLastSyncedCommit`/`setLastSyncedCommit` round out the sync-pointer bookkeeping. Shelled out via `execFileSync` with an argument array (never an interpolated shell string), avoiding command injection entirely.
**13 tests, all against real, disposable temporary git repositories** — no mocking of git itself anywhere.
**Two real bugs found while writing those tests — both in the tests, not the service:** a "combined changes" fixture captured its comparison baseline *before* creating files it later modified within that same range, so their net effect correctly collapsed to "added" rather than the intended "modified"/"renamed" — the exact same collapsing-across-commits behavior already proven, just momentarily forgotten while authoring a fixture. And the original near-total-rewrite fixture shared zero literal lines by accident, genuinely testing the wrong thing (an undetectable case) until a single deliberately-preserved line made it a meaningful test of the threshold actually doing its job.

### 23. Left open, deliberately, at a natural stopping point
**What's fully done:** `GitService` itself — diffing, categorization, threshold, sync-pointer bookkeeping — standalone and tested, matching the original roadmap split.
**What's designed but not yet built:** the orchestrator (tentatively `SyncService`) that actually chains `GitService`'s output into `DocumentationService` — renamed → `renameFile` → `checkFile`; modified/added → `checkFile`; deleted → the message-then-delete handler from §21.
**One decision recommended, not yet implemented:** first-run behavior (no stored pointer yet) should do a full scan, treating every existing file as newly added, rather than silently bootstrapping from "now" — matching standard practice for incremental indexing/sync tools generally, and the only choice that surfaces any value for a user adopting the tool into a pre-existing, undocumented codebase rather than a greenfield one.

## Objective 3.5 — Wiring the Engine: SyncService

### 24. The three chains, decided the previous session, now actually implemented
**Shape:** `deleted` → `handleDeletedFile` (already existed); `renamed` → guarded `renameFile` → `checkFile` chained immediately; `added`/`modified` → `checkFile` directly.
**Extracted as its own method on purpose:** `handleRenameEvent` was pulled out of `sync()`'s inline loop body specifically because `LiveWatchService` would need the identical logic later — avoided duplicating it before it was even written twice.

### 25. Two correctness guards needed, found by reasoning through the failure modes, not by a failing test
**`renameFile` throws if the old file was never documented** — a very common case, since most files have no `DocRecord` at all. Guarded with an `existsSync(storagePathFor(oldPath))` check before calling it; `checkFile` still runs unconditionally on the new path regardless, since it already handles "no prior storage" gracefully on its own.
**`checkFile` must never run on a non-source file** — an ordinary commit touching `README.md` would otherwise crash the whole sync. Filtered by extension before every `checkFile` call, in every code path (`sync`, `fullScan`, `reconcile` later).

### 26. First-run behavior decided last session, built this one
**Confirmed and implemented:** `lastSyncedCommit === null` triggers a full scan across every git-tracked file (flagging undocumented nodes from day one), then sets the pointer — rather than silently bootstrapping from "now" and missing an entire pre-existing, undocumented codebase.

### 27. Verified with real, fully-wired integration tests, not mocks
**9 tests**, built from real `AstService`+`DocumentationService`+`GitService`+`SyncService` instances against real temporary git repos: first run, no-op when nothing changed, each category individually, and a combined multi-category diff in one sync.

## Objective 3.6 — Understanding NestJS's Module System to the Actual Mechanism

### 28. The core misconception directly disproven, not just explained
**The claim under test:** does `SyncService`'s own `import { DocumentationService } from "../ast/documentation.service.js"` mean it can use it, independent of `@Module()` wiring?
**Disproven by removing `AstModule`'s `exports` array and rebuilding:** a real `UnknownDependenciesException`, thrown by NestJS's own `Injector`, even though the TypeScript import line was completely untouched and still compiled cleanly. Proved NestJS's DI graph is a *runtime* concept the `Injector` walks by reading `design:paramtypes` metadata (the same mechanism proven back in Objective 3.1) — entirely separate from the compiler's own module resolution, which was already satisfied.
**Restored and reconfirmed immediately after**, isolating the one change.

### 29. Providers can inject other providers, not just controllers — already proven, just made explicit
`SyncService`'s own constructor, injecting `GitService` and `DocumentationService`, is the proof already sitting in the codebase — no controller involved anywhere in that chain.

### 30. Tested, not assumed: can a bare provider go directly into another module's `imports` array?
**TypeScript compiled it with zero errors** — a `@Module()`-decorated class and an `@Injectable()`-decorated class are the same type to the compiler; decorators attach metadata, they don't change what a class *is*.
**NestJS's own `DependenciesScanner` rejected it at runtime** with a distinctly different, explicit exception (`InvalidClassModuleException`), naming the exact mistake and the fix in its own message. Confirms `imports` can only ever contain `@Module()` classes, never bare providers — a hard runtime rule enforced by Nest itself, not a style convention that happens to be followed.
**Restored `imports: [AstModule, GitModule]`** afterward; full suite green again.

## Objective 3.7 — Live Watching: Catching Uncommitted Changes From Any Tool

### 31. The core question, reconciled precisely across several rounds of back-and-forth
**Settled, for both halves of the problem:** does it matter which tool (VSCode, `cmd`, File Explorer) performs an action, versus whether the app's own interface was used? No, for committed changes (git diffing is tool-agnostic by construction — a commit only ever records the end state, never which tool produced it) and no, for live/uncommitted changes either (OS-level file watching observes the filesystem itself, not any one program's actions). **The only real variable is whether the app's process happens to be running at that moment — not whether it's the one being actively used.**

### 32. The zero-shared-lines limit, revisited until the framing was actually correct
**Re-confirmed concretely:** a total rewrite-and-rename produces byte-for-byte identical git trees whether performed via `git mv`, manual delete-then-create, or a plain OS `mv` command — proving the ambiguity is a property of the *committed content itself*, not of any tool or mechanism, and applies equally to reconstructing one's own past commits, not only a collaborator's.
**A real correction to an earlier overstatement:** letting a delete-and-add fall through uncorrelated is not a silent catastrophe once a real deletion handler exists that *surfaces* (rather than hides) what it removes — the actual cost is losing automatic continuity of old prose, not silent breakage. That softer framing is itself conditional on the deletion handler doing its job, which by this point it does.

### 33. Architecture chosen specifically so none of our own code needs to be platform-specific
**Detection delegated entirely to `chokidar`** (already present as a project dependency, pulled in transitively by NestJS's own tooling) — independently battle-tested across the whole JS ecosystem, rather than hand-rolling per-OS bindings ourselves.
**Similarity computation delegated entirely to git itself**, after discovering — and proving with a real, repo-free test — that `git diff --no-index -M<threshold>` performs full rename-pairing between two arbitrary directories, needing zero commits and zero repository, with identical behavior regardless of host OS. Reuses the exact proven algorithm from `GitService` rather than writing a second one.
**Net effect:** the only genuinely new code (correlation and timing) is pure, platform-agnostic JavaScript — none of it carries platform-specific risk itself.

### 34. Two ordering assumptions, proven wrong by direct measurement rather than corrected in advance
**Raw `fs.watch` on this machine reliably fired a rename's two underlying events ~2ms apart, unlink-side first.** A standalone chokidar probe script, logging real timestamps and run three times to rule out a fluke, measured the *opposite*: chokidar's own higher-level processing delivers `add` reliably ~90-100ms **before** `unlink` for the identical rename operation.
**Redesigned the correlation logic to be fully symmetric** — either ordering must resolve correctly — rather than assuming the lower-level result would generalize upward.

### 35. A self-match bug, found by reasoning through an actual failure, not by guessing at fixes
A freshly created file gets cached and registered as a "pending add," in case some future unlink turns out to be its rename partner. When that *same* path was later deleted, the unlink handler matched it against its own still-pending entry — 100% self-similarity, trivially — consuming the pairing before the real rename's other half ever arrived. Fixed by explicitly excluding same-path matches in both correlation directions.

### 36. A test-timing bug distinguished from a service bug, by adding real instrumentation instead of re-guessing
Three tests kept failing identically even after the ordering fix. Temporary debug logging on the watcher's actual events (not more assertions) showed the events simply weren't firing in time — because the tests deleted/renamed files synchronously, immediately after creating them, giving chokidar no time to register the original creation first. Fixed in the tests (added real settling delays), not the service — "the code is wrong" and "the test is wrong" stayed open hypotheses until actually checked, rather than the first one assumed by default.

### 37. Verified end to end against a real chokidar watcher, no mocking anywhere
**6 integration tests:** a pure rename, a rename combined with a partial rewrite (via the same lenient threshold as the git path), a standalone deletion once its correlation window expires, a standalone addition once its window expires, a same-path modification (no correlation needed at all), and non-source files ignored entirely.

## Objective 3.8 — Scenario 2: Reconciling What Happened While the App Was Closed

### 38. Precisely scoping what this can and cannot do, before writing any code
**A genuine third gap, reconciled directly against the other two:** live-watching only ever sees what happens while its own process is running; git-sync only ever sees what's been committed. Anything uncommitted while the app was closed the entire time is invisible to *both* — not already covered by either existing mechanism.
**Explicitly cannot correlate renames, by design, not by oversight:** a one-time snapshot comparison has no timing signal and no cached prior content to diff against, so an uncommitted rename here degrades to the same uncorrelated delete-and-add as the hardest git case.

### 39. Two small capabilities, each proven independently before being combined
**`GitService.listWorkingTreeFiles`:** unlike `listTrackedFiles` (committed/staged only), reconciliation needed `git ls-files --others --exclude-standard --cached` specifically to catch a file the user created and never even staged — confirmed directly, including that an *uncommitted* `.gitignore` file still takes effect immediately.
**`DocumentationService.listDocumentedFileIds`:** reconciliation needs to check every *existing* record against current disk state (to catch deletions), not just scan forward from files that currently exist — required enumerating `storage/` directly rather than deriving a file list from anywhere else.

### 40. A real crash found while testing, not anticipated in the original design
`git ls-files --cached` still lists a file based on git's index even after it's been deleted from disk without `git rm`. The first implementation called `readFileSync` unconditionally on every listed path and threw `ENOENT`. Fixed with the exact same `existsSync` guard pattern already established in `handleFileEvent`, rather than inventing a new one.

### 41. Confirmed by test, exactly as scoped: an uncommitted rename produces two honest, disconnected signals
The old file's record surfaces its `docText` (available for manual recovery) and gets removed; the new file shows up as ordinary, separately undocumented content. Not a false rename, and not silently lost either — precisely the accepted limitation stated going in, now proven rather than assumed.

## Objective 3.9 — Manual Recovery: The Archive Mechanism

### 42. Why this needed to exist at all, stated precisely rather than as a consolation feature
Not a fallback for imperfect automatic detection — a genuinely separate category of fix. A human who remembers performing a rename has context (their own memory of intent) that no algorithm operating on content alone could ever reconstruct — including the git case proven permanently undetectable much earlier (zero shared lines) and Scenario 3.8's app-closed gap. Once a limit is proven genuinely permanent, the correct fix is a human-verified escape hatch, not an ever-cleverer heuristic chasing an unreachable target.

### 43. Mechanically a `writeDoc` convenience, explicitly not a resurrected `renameFile`
An archived record's hashes belong to a file that no longer exists, so there's nothing to migrate — attaching computes entirely fresh hashes against the target file's real current content, using the archived `docText` only as a pre-filled starting draft.
**A precise distinction drawn out by direct question:** `highlightStart`/`highlightEnd` still has to be supplied even here, because it answers a completely different question from what the hash answers. The hash is *identity* — position-invariant, which is why it survives future moves and reformatting. The highlight range is *selection* — an inherently positional, one-time lookup used to find which AST nodes the human is pointing at right now, then discarded; it's never stored in a `DocRecord` at all. Attaching an archived record to a new file is still a fresh selection, no different in kind from documenting anything for the first time — the archive only ever supplies the text, never the location.

### 44. Per-record granularity, not per-file, confirmed by tracing the actual data shape
`handleDeletedFile`'s archiving loop runs once per `DocRecord`, so a file that had three separately-documented highlights produces three independent archive entries, sharing only a common `originalFileId` field (kept for potential future grouping in a UI, not used by the mechanism itself). `attachArchivedRecord`/`discardArchivedRecord` both operate on exactly one entry at a time — there's no bulk "handle everything from this file" operation, since unrelated pieces of old documentation have no guarantee of belonging with the same replacement.

### 45. A real bug in a different, already-existing method, found while building this one
`listDocumentedFileIds` iterates every `.json` file in `storage/` and parses each as a per-file record — but the new `_archive.json` is a flat array, not that shape, and would have been silently misparsed, pushing `undefined` into the fileId list. Fixed with an explicit exclusion, plus a regression test guarding it specifically.

### 46. Verified against real, uniquely-marked data, with a known test-only caveat named honestly rather than hidden
**8 tests**, all against real file operations. `_archive.json` is the one piece of storage that isn't scoped per-file the way ordinary records are — a genuine shared-file race under Jest's parallel workers, though not a real concern in production (a single Electron process has no such concurrency at all). Tests assert on specifically marked content rather than exact counts or array equality, and the full suite was run twice back to back to confirm no flakiness in practice.

### 47. Where this leaves the roadmap
**Fully done:** the whole documentation-drift engine's detection surface — git-history sync, live-watching with rename correlation (any tool, while the app is open), startup reconciliation (uncommitted, app-closed gap), and manual recovery (whatever automatic detection provably cannot resolve).
**Not yet built:** the Electron renderer/UI itself (still just the "it's alive" static shell from Objective 3.3); the IPC layer connecting a real interface to these services (`NestFactory.createApplicationContext()` was proven viable back in Objective 3.2 §9, but never actually wired up); the main-process bootstrapping that decides *when* `sync()`/`reconcile()`/`LiveWatchService.start()` actually get called during the app's real lifecycle; and a UI for browsing and attaching archived records (currently service methods only, no surface to use them from).
**A real architectural gap worth naming plainly:** `DocumentationService`'s storage still lives at a fixed `storage/` path relative to wherever the Node process happens to be running from — not inside the target repository at all, and therefore not yet the git-tracked, collaboratively-mergeable `.rapid-docs/`-style location decided back in Objective 3.2 §10. Until storage moves to be repo-relative, the git-native documentation-collaboration story is designed and reasoned through, but not actually realized.

## Objective 3.10 — Closing the Storage-Location Gap: `repoPath`, Relative Identity, Mirrored Structure

### 48. The real bug underneath "storage is in the wrong place" — this was about identity, not just location
`fileId` had always been a full absolute path, sanitized directly into a storage filename. Two collaborators cloning the same repo to different absolute paths (different machines, different usernames, even different OSes) would compute two different, never-colliding filenames for what's supposed to be the *same* file's documentation — silently defeating the entire git-native collaboration premise before a single merge was ever attempted. Named plainly rather than glossed over back in §47.

### 49. Two real industry patterns weighed, one chosen for a reason specific to this tool
Considered content-hash-based storage (git's own object model, webpack's persistent cache — collision-proof, but opaque) against directory mirroring (TypeScript's `--declaration` output, Istanbul coverage reports, Jest's `__snapshots__` — equally collision-proof, since a filesystem can't have two files at one path, and inherits that guarantee for free). Chose mirroring specifically because this tool's whole premise is git-diffable, git-mergeable documentation: a hashed filename in a `git diff` tells a reviewer nothing about which file changed; `.rapid-docs/src/math.ts.json` tells them immediately.

### 50. The refactor's actual shape: split one absolute path into two separate concerns
Every `DocumentationService` method changed from taking one `fileId`/`sourcePath` to taking `repoPath` (where the repo, and `.rapid-docs/`, lives) plus a repo-relative path (the stable, cross-machine identity — the only thing ever stored as `fileId`). Propagated through `SyncService` (now passes `repoPath` and relative paths straight through, instead of pre-joining to an absolute path) and `LiveWatchService` (converts chokidar's absolute paths back to repo-relative via `path.relative`).

### 51. A real cross-platform correctness requirement, tested rather than assumed
Git's own relative-path output is always forward-slash, regardless of host OS; Node's `path.relative()` on Windows returns backslash-separated results. Left unnormalized, the same logical file discovered via git-diffing versus via live-watching would produce two *different* identity strings on Windows, silently splitting one file's documentation into two unrelated, untracked storage entries. Normalized at the one boundary where chokidar's absolute paths get converted, and proved it with a real test: document a nested file directly, then edit it live, confirming the live-detected identity actually matched the one `writeDoc` had already used.

### 52. A genuine side effect on the test suite, not a design goal in itself
Since documentation now lives inside `repoPath` rather than at a fixed location relative to wherever the process happens to start, every test's storage became naturally isolated to its own temporary `repoPath` — including the shared-file concurrency risk named honestly back in Objective 3.9 (§46), specific to `_archive.json`. That risk is now gone by construction, not by added locking.

### 53. Verified end to end, and legacy artifacts cleaned up rather than left to rot
All three services' entire test suites rewritten against the new signatures — 80 tests total, full suite run twice back to back to confirm stability. Leftover artifacts from the old scheme (a stale `storage/_archive.json` at the project root, and an emptied `__test-fixtures__` directory) removed once confirmed dead, rather than left behind.

### 54. What this closes, and what it doesn't
**Closed:** the real architectural gap named in §47 — documentation now genuinely lives inside the target repo, keyed by a stable, cross-machine identity, in a structure that mirrors the source tree exactly. The git-native collaboration story is no longer just reasoned through; the storage layer it depends on now actually exists.
**Still open, unchanged by this fix:** the Electron renderer/UI, the IPC layer, main-process bootstrapping deciding when `sync`/`reconcile`/`LiveWatchService.start` actually run, and a UI surface for the archive mechanism.

## Objective 3.11 — A Real Gap Found While Explaining, Not While Building

### 55. The question that surfaced it
Asked precisely: if a file already has documentation and gets moved to a different folder, is the whole storage scheme "path dependent," and does that mean the docs get lost? Answered in principle first (no — the rename-correlation machinery across `GitService`/`SyncService`/`LiveWatchService` exists exactly to prevent that) — then tested the specific claim directly, live, through a real cross-folder move, rather than resting on the principle alone.

### 56. The real bug the demonstration exposed
A file that existed *before* `LiveWatchService.start()` was called, and had never been individually touched since, had no entry in the content cache — because chokidar's `ignoreInitial: true` deliberately never fires `"add"` for pre-existing files, and the cache was only ever populated reactively, inside `handleAdd`/`handleChange`. Moving such a file produced two independent, uncorrelated events (a plain deletion, a plain undocumented addition) — even though the content was 100% identical. Confirmed directly this is not the rare zero-shared-content case from Objective 3.7: it's the much more common "the very first live action taken on an untouched file is to move it."

### 57. The fix: prime the cache upfront, from machinery already trusted
`start()` now makes one upfront pass over every file `GitService.listWorkingTreeFiles` reports (the same git-aware, gitignore-respecting listing `reconcile()` already relies on), caching each file's current content silently — no messages emitted, since this is priming for correlation, not reporting a change. A direct consequence, found immediately by rerunning the suite: `LiveWatchService.start()` now requires a real git repository, matching every other part of this tool's existing assumption — every existing test broke, since none of them had actually initialized a git repo for the watched directory. Fixed at the test level (added real `git init` setup to match `SyncService`'s own test conventions), not by relaxing the service.

### 58. Verified against the exact scenario found, and folded permanently into the suite
A dedicated regression test reproduces precisely what was found manually: stop the already-running watcher, create and commit an already-documented file, start watching for the first time, then move it without ever touching it live first. Whole suite: 81 tests, 5 files, passing.

## Objective 3.12 — Main-Process Bootstrapping: `WorkspaceService` and the Real Engine Wiring

### 59. `WorkspaceService`: repo selection, kept deliberately Electron-free
Built as a plain, testable NestJS service with zero Electron dependency — takes `userDataDir` as an explicit parameter rather than hardcoding Electron's `app.getPath("userData")` internally, the same reasoning that moved `DocumentationService` off a fixed storage path. Keeps it fully Jest-testable without the real Electron module ever needing to resolve, sidestepping the whole earlier module-resolution saga entirely rather than re-fighting it.

### 60. The bootstrap sequence, confirmed and built as agreed
`sync()` first (commits), then `reconcile()` (uncommitted-while-closed), then start `LiveWatchService` — both one-shot calls' results combined into a single reveal, live-watching started immediately after with no wait, since starting it produces nothing to wait for.

### 61. A real, disproven prediction: dynamic import from CommonJS *does* load the ESM output
Predicted, from watching TypeScript down-level `await import(...)` into `Promise.resolve().then(() => require(...))` for a CommonJS compile target, that this would fail at runtime — plain `require()` cannot load a genuine ES module. Tested directly against the real compiled output, inside the real `electron.exe` process — it worked. Whatever mechanism actually resolves this (likely Electron's own Node integration handling the interop differently than plain Node would), the prediction was wrong, and only real execution revealed that — a reminder that even a well-reasoned guess about this exact CJS/ESM boundary needs checking, not trusting, given how many genuine surprises it's already produced in this project.

### 62. A real, live bug found by the very first real test run: a shared, unbranded userData folder
The first bootstrap test picked up a completely unrelated repo path (`C:\Users\obolo\bchiang7-v4`) neither of us had configured. Traced to its actual cause: `app.getPath("userData")` resolved to the generic `%APPDATA%/Electron` folder, shared by *any* unbranded Electron app on the machine — not a hypothetical risk, an actual pre-existing file on this real machine, almost certainly from a completely unrelated application. Left untouched deliberately (not something created for this project, sitting in a shared system location). Fixed with `app.setName("rapid-docs")`, called explicitly rather than relying on Electron's own auto-detection from `package.json`, which — confirmed directly — did not reliably find it when launched as a raw script path rather than a packaged app. Verified the fix directly: userData path changed to the properly-scoped `%APPDATA%/rapid-docs`.

### 63. Two more real findings from a clean, controlled end-to-end test
**Message duplication:** `sync()`'s first-run scan and `reconcile()`'s always-run scan both independently rediscover any currently-unresolved issue, since `checkFile` is a pure, repeatable read that never "consumes" a problem once reported — confirmed directly (the same message appeared twice in real output). Fixed by deduplicating the combined message list by exact content, in `electron/main.ts` specifically — a presentation-layer concern, not a change to what `sync()`/`reconcile()` themselves correctly report.
**A crash-safety gap, same shape as several found earlier in this project:** one unparseable file threw uncaught out of `checkFile`, aborting the entire batch scan for every other file — and the same code path is what a live edit goes through, meaning a user mid-typing an incomplete function (an entirely normal thing to do) could crash the whole live-watching session over a momentary syntax error. Fixed at the single, shared point every caller goes through (`SyncService.checkAndReport`), converting a parse failure into a graceful error message instead of letting it propagate — protecting `fullScan`, `sync`, `reconcile`, `handleFileEvent`, and `handleRenameEvent` all at once. Verified two ways: a real Jest regression test (a broken file sitting between two good ones, confirming both good files still get checked), and by rerunning the actual Electron bootstrap against exactly that scenario.

### 64. Verified end-to-end, in the real Electron process, not just Jest
The full sequence — persisted-repo lookup, `sync`, `reconcile`, deduplication, crash resilience, live-watching startup — confirmed together against a real, controlled test repo (one good file, one deliberately broken file), inside the actual `electron.exe` binary. Whole Jest suite: 87 tests, 6 files, passing; the main NestJS app boots cleanly with `WorkspaceModule` confirmed in the dependency graph.

Main-process bootstrapping is done. Still open: the IPC layer connecting a real renderer UI to these services, the renderer UI itself (including the highlight-selection design decision), and the archive UI — with one design question still explicitly undecided: whether the archive gets a smart, content-based match suggestion (would require extending `ArchivedRecord` to also capture the original snippet) or stays a passive browse-and-attach screen.

## Objective 3.13 — The IPC Layer: Proving the Mechanism, Then the First Real UI Screen

### 66. The core mechanism, explained and proven before any real design
Electron's renderer is, by design in any secure modern setup, completely sandboxed from Node — `contextIsolation: true`, `nodeIntegration: false`. A preload script is the one deliberately narrow bridge: it runs with privileged access before the page loads, and `contextBridge.exposeInMainWorld` lets it hand-pick specific named functions onto `window` — never the raw `ipcRenderer` object itself, which would let any page script send arbitrary IPC messages.
Proven with the smallest possible real example: one channel (`"ping"`), verified via Playwright reading the actual rendered page text (`"ipc: pong"`), not assumed.

### 67. Two recurring bugs, both already-known issues, both resurfacing
**`ELECTRON_RUN_AS_NODE=1`** — the exact environment variable from when this Electron shell was first built — was set again in this session, breaking Playwright's launch with the same generic `"Process failed to launch!"` error. Diagnosed the same way as before (run `electron.exe` directly for a clearer signal), fixed the same way (unset for the specific launch command).
**A stale `electron/dist/index.html`** — `tsc` only compiles `.ts` files, so edits to the source `index.html` were invisible until manually copied, a gotcha noted in passing once before and now hit again for real. Fixed properly this time, not just worked around: added `build:electron` and `build:all` npm scripts that compile and copy static assets together, so it can't be silently forgotten a third time.

### 68. The channel design: organized by what the UI needs to do, not a 1:1 mirror of every service method
Grouped into workspace (current repo, switching repos), files (list, read — genuinely new, not an existing service), documentation actions (mirroring `DocumentationService`), archive (mirroring the archive methods), and messages (push-based, `webContents.send`, fundamentally different from the request/response shape of everything else, since these happen on main's own schedule).
Deliberately scoped to build only what the first real screen needs, rather than the full surface speculatively — the same anti-over-engineering principle applied everywhere else in this project.

### 69. Highlight selection: Electron provides none of this, by design
Electron is Chromium + Node, nothing more — no code editor, no text-selection capability of its own; the renderer is just a webpage, and whatever capability exists has to come from ordinary web development. Two real tiers considered: a plain `<textarea>`'s native, zero-dependency `selectionStart`/`selectionEnd`, versus Monaco (the actual editor VSCode itself uses, extracted specifically for embedding elsewhere). Chose the plain textarea for now, deliberately — proves the whole pipeline (list, read, select, document) with zero new dependencies, leaving Monaco as a later, contained swap of one display widget, not a rethink of anything else.

### 70. The first real UI screen, built and verified end-to-end
`files:list` (wrapping `GitService.listWorkingTreeFiles`, filtered to source files) and `files:read` (a genuinely new capability — nothing in the engine had ever needed to hand raw content back out before, since every service only ever returns derived things: hashes, reports, messages). ### 71. Highlight capture wired to `writeDoc`, verified with real evidence on disk
`textarea.selectionStart`/`selectionEnd` (the plain, native, zero-dependency selection mechanism chosen in §69) captured on a button click, passed through a new `docs:writeDoc` channel to `DocumentationService.writeDoc` unchanged — no new logic on the main-process side beyond a thin pass-through. Answer: not yet, deliberately — the current UI is 100% functional scaffolding with zero visual design intent, for two concrete reasons: the app's full shape isn't known yet (messages and archive screens still ahead), and the centerpiece of the whole app (code display) is a placeholder specifically because it's planned to become Monaco later, which will shape a lot of the surrounding visual language on its own. ## Objective 3.14 — A Real Bug in `findDocumentedNodes`, Found by Using the App, Not by Reading Code

### 74. The bug, as it actually presented in the UI
Documented only the `add` function in a two-function file (`add(a, b)` and `sub(a, b)`, deliberately sharing parameter names). Clicking the resulting row in the documented-sections panel selected `{0, 89}` — the entire file, both functions — instead of `{0, 45}`, just `add`. Caught by using the real UI, not by inspecting `findDocumentedNodes`'s code in advance; nobody was looking for this specific bug.

### 75. Verify before blaming proven logic — the user's direct instruction
The immediate temptation was to suspect `writeDoc`, since that's where the record actually gets built. The user stopped that line of reasoning explicitly, insisting on checking real evidence before proposing any fix to something "rigorously tested." Read the actual `.rapid-docs/src/math.ts.json` off disk: it held exactly 10 members, all real structural hashes belonging solely to `add` — nothing referencing `sub`. That proved `writeDoc` was correct, and the bug had to be isolated entirely to the read side (`findDocumentedNodes`), narrowing the search before writing a single line of fix.

### 76. Root cause: individual-hash matching against a position-invariant hash scheme
`findDocumentedNodes` (a Phase 1/2-era method, from before mirrored storage existed) worked via `buildReverseIndex` — flattening every stored record into single `hash → recordId` entries, then matching any current AST node whose hash appeared in that index. Structural hashing is deliberately position-invariant (Phase 1's whole point: a function's meaning shouldn't change hash just because it moved in the file). But that same property means two different functions' identically-named parameters — `add`'s `a`/`b` and `sub`'s `a`/`b` — hash to byte-identical values. A single shared hash match against `sub`'s `a`/`b` was enough for the old code to wrongly pull `sub` into `add`'s documented record.

### 77. The fix: verify the whole combined record, not any one member
`writeDoc` already computes `recordId` as the hash of the *sorted, combined* list of every matched member's hash — not any individual hash — which is exactly what makes it collision-resistant in the first place. `findDocumentedNodes` had never replicated that combined computation; it checked members individually. The fix makes it do the same sort-and-hash `writeDoc` does, per candidate node span, and only accepts a match when the *complete* set of member hashes reconstructs a stored `recordId`. One shared identifier hash is no longer sufficient — the whole record has to line up. `buildReverseIndex` became fully dead code once this landed (confirmed via Grep: zero remaining callers) and was deleted outright.

### 78. Verified twice: unit tests, then the real app again
Added a regression test reproducing the exact scenario (shared parameter names, only one function documented, asserting the returned span stays inside that function). Updated the one pre-existing test whose assertion (`found.length === 16`) had encoded the *old, buggy* per-node-fragment behavior rather than the correct one-entry-per-record behavior. Full suite: 88/88 passing. Then rebuilt (`build:all`) and reran the real Playwright-driven Electron flow against a clean copy of the same two-function repo: clicking the row now selects exactly `{0, 45}` — `add` only, not `sub`. Same bug, same repo, now provably fixed at both levels — not just "the test suite is green."

## Objective 3.15 — Message-Display Channels, and a Second Real Bug Found the Same Way

### 79. Two message sources, two genuinely different IPC shapes
Catch-up messages (from `sync()`+`reconcile()`, already computed once at bootstrap, previously only `console.log`'d) are a fixed list the instant bootstrap finishes — naturally **pull**: `ipcMain.handle("messages:getCatchUp", () => catchUpMessages)`, asked for once when the renderer loads. Live messages (from `liveWatchService.on("messages", ...)`, arriving at unpredictable times after the window is already open) have no natural "ask" moment — naturally **push**: `mainWindow.webContents.send("messages:live", ...)`, requiring a stored `mainWindow` reference that `createWindow()` had never kept before.

### 80. The bug, found the same way as `findDocumentedNodes`'s: by actually using the feature
Built a real two-message scenario (a documented function with an uncommitted edit that partially drifted it, plus a second, entirely undocumented function) and drove it through the live Electron app. Catch-up correctly showed both messages. Then, mimicking an external edit while the app was watching, added a third, unrelated function — and the panel didn't just gain the one new message; it re-displayed the *original two* a second time as well. Root cause: `checkFile`/`generateMessages` are pure, repeatable reads of a file's CURRENT state (the same property that made `sync()`+`reconcile()` overlap, back in §67's `dedupeMessages`) — so any edit to a file re-reports every still-true problem in it, not just what changed, and a renderer that only ever *appends* what it receives will duplicate forever.

### 81. Why "just dedupe" was rejected in favor of the more correct fix
The cheap fix — skip re-adding a message if its exact text was already shown — was rejected after thinking through what it actually means for a drift detector: it would make duplication *look* fixed, but a genuinely-resolved problem (user documents the file, warning becomes false) would never be removed either, since dedup only prevents ADDING, never removes. That directly contradicts the tool's purpose: showing *current* problems, not a history log. The correct model — matching how VSCode's Problems panel, ESLint, and TypeScript diagnostics all behave — is: each time a file is re-checked, REPLACE that file's messages with what's true right now.

### 82. What "replace, not append" required, structurally
`Message` gained a `relativePath` field (it previously carried only `severity`/`text`) — added at its one real interface definition in `documentation.service.ts`, and threaded through all 5 places a `Message` object literal is actually constructed (3 in `generateMessages`, 1 in `handleDeletedFile`, 1 in `SyncService.checkAndReport`'s parse-failure catch). `LiveWatchService`'s `"messages"` event changed from `(messages: Message[])` to `(relativePaths: string[], messages: Message[])` — the `relativePaths` list is what lets a listener correctly clear a file's entries even when `messages` comes back completely empty (a file becoming clean carries no signal at all if the only thing emitted is an empty array with no attached identity). A rename touches two identities (old path — gone entirely, must be cleared; new path — gets whatever the fresh check found), everything else touches exactly one; each of the 6 real call sites in `live-watch.service.ts` already knew which case it was in, structurally, so no new inference was needed, just passing along what was already known.

### 83. The design: main process holds the truth, renderer only ever renders a snapshot
`messagesByFile: Map<string, Message[]>` in `main.ts`, seeded once from the catch-up pass (grouped by `relativePath`) and updated by every live event via `replaceFileMessages(relativePaths, messages)` (delete the named entries, then repopulate from `messages`). Every live push sends the FULL flattened current snapshot, not just the batch's delta — the renderer's `onLiveMessages` handler and its startup `loadCatchUpMessages` now share one `renderMessages()` function that unconditionally rebuilds the panel from whatever list it's given. This is deliberately the simplest correct design: no dedup logic, no partial-update logic, and no possibility of the renderer's view drifting from the main process's, since the renderer never accumulates anything on its own.

### 84. A related, smaller bug caught while touching the same code: `dedupeMessages` could hide a real problem
`dedupeMessages` (from §67) deduped catch-up messages by `severity::text` alone — with `relativePath` now available, that key was too coarse: two different files whose undocumented nodes happen to fall on the same line number (a common, plausible coincidence, e.g. two small files each starting with a function on line 1) would produce byte-identical message text and silently collapse into one entry, hiding one file's real, distinct problem. Fixed by keying on `severity::relativePath::text` — found and fixed as a direct consequence of finally having the information needed to see it was wrong, not from a separate investigation.

### 85. Verified with real evidence, same scenario, before and after
Built the exact repro (documented `add` with a live, uncommitted partial-drift edit, plus undocumented `mul`) and drove it through the real app twice. Before the fix: editing the file externally re-displayed the original two messages alongside the new one. After the fix: catch-up correctly showed 3 rows (the warning about `add`, plus info for two undocumented functions); externally editing the file to actually FIX `add`'s drift dropped the panel to exactly 1 row — the warning about `add` disappeared entirely (not just "stopped growing"), while the still-true message about the other function remained, with no duplicates. Full suite (including new regression coverage in `live-watch.service.spec.ts` for the `relativePaths` contract on both a plain change and a rename): 88/88 passing.

### 86. What's left
Archive browsing/attach — the last screen from the originally-confirmed UI plan — to be added the same incremental way as everything else.

## Objective 3.16 — Archive Browsing/Attach: the Last Screen, and Purely Wiring This Time

### 87. No new backend logic needed — the service layer already had everything
Unlike every other screen so far, this one added zero new methods to `DocumentationService`: `loadArchive`, `attachArchivedRecord`, and `discardArchivedRecord` (Phase 2/3-era, built for the manual-recovery design in §219's Objective 3.9) already covered listing, re-attaching archived text to a fresh selection, and permanent removal. The work was exactly three thin `ipcMain.handle` pass-throughs (`archive:list`, `archive:attach`, `archive:discard`), matching `docs:writeDoc`'s shape exactly, plus the UI.

### 88. UX shape: select-then-act, matching the rest of the app's existing pattern
An archived record can't be attached the instant it's clicked — the destination (which file, which exact range) doesn't exist yet as a selection. So clicking a row marks it "pending" (visually highlighted) rather than acting immediately; the user then selects code in the open file (the same native `textarea` selection every other screen already uses) and confirms with a separate "Attach here" button — deliberately the same select-something-then-confirm-with-a-button shape as the existing doc-writing bar, not a new interaction pattern invented just for this screen. Discard, by contrast, needs no destination and no confirmation step, so it's a single button per row.

### 89. Verified with a real three-file scenario, both actions in one run
Built a real repo: two documented files deleted without committing (so `reconcile()`'s existing deletion-handling path — proven back in Objective 3.9 — archives both automatically at startup) and one untouched file as an attach target. Drove it through the real Electron app: both archived records appeared with their correct origin file and text; discarding one left exactly the other; marking the remaining one pending, selecting a range in the untouched file, and clicking "Attach here" produced a new documented-sections entry with the archived text, and the archive panel went back to empty. Every step confirmed against actual rendered DOM state, not assumed from the IPC call succeeding.

### 90. The UI plan, confirmed complete
File browsing, highlight-capture/`writeDoc`, the documented-sections panel, catch-up/live messages, and now archive browsing/attach — every screen from the originally-scoped plan (back when Monaco and real visual design were deliberately deferred in §72) now exists in some functional form. Real visual design work — the single, informed pass deferred until the app's whole shape was known — is the natural next decision point, not a continuation of this incremental build-one-screen-at-a-time phase.

## Objective 3.17 — An Evidence-Based Audit, Not an Assumption, Then Three Fixes

### 91. "Do we have everything" answered by grepping, not by recalling the plan
Asked directly whether the app now covered everything a user would want to do. Rather than reason from memory of what had been built, the actual answer came from listing every public method on every service (`DocumentationService`, `GitService`, `SyncService`, `LiveWatchService`, `WorkspaceService`) and cross-checking each one against `main.ts`'s `ipcMain.handle` calls, `preload.ts`'s exposed bridge, and `index.html`'s actual `window.rapidDocs.*` call sites. Three real gaps surfaced this way that a plan-level review would have missed entirely, because the earlier three-mode design discussion had been reasoning about *services that exist*, not about *which of their methods had ever been wired to a button*.

### 92. Gap 1 (most severe): `writeDoc`'s own error message pointed at a door that didn't exist
`writeDoc` deliberately refuses to overwrite an exact-match record, telling the caller: `"...Use editDocText to change its text instead."` Neither `editDocText` nor `deleteRecord` had any `ipcMain.handle`, any `preload.ts` exposure, or any UI affordance at all — a real user hitting that exact error, doing exactly what the app told them to do, would have hit a dead end. Fixed with `docs:editDocText`/`docs:deleteRecord` channels (same thin-pass-through shape as `docs:writeDoc`) and inline Edit/Delete buttons on each documented-sections row (Edit swaps the text for an input; Enter saves, Escape/blur cancels — deliberately no separate confirm step for either, matching the archive panel's existing no-confirmation Discard button).

### 93. A second, unrelated bug found purely by testing gap 1 for real
Verifying the fix required a wider Electron window than the app had ever used (four fixed-width columns — file-list, documented-sections, archive-panel — total 740px alone), and the real Playwright run hit an actual click-interception failure: `documented-sections` was overlapping `content-pane`'s buttons at the original 800×600. The window size had been chosen back when only 2-3 columns existed and was never rechecked as columns were added. Fixed by resizing to 1280×800 — still scaffolding, not real design, but scaffolding has to actually fit its own content, and this would not have been caught without actually running the app at its real size.

### 94. Gap 2: repo-switching existed as a dialog, not as a feature
`determineRepoPath` only ever ran once, inside `bootstrapEngine`, at startup — there was no channel for the renderer to reach it again, and a canceled dialog left the whole app silently empty with zero explanation. The real design cost wasn't the dialog itself but `LiveWatchService`: `start()` creates a brand-new chokidar watcher and overwrites its own internal handle with no regard for whether a previous one was still running, so switching repos without an explicit `stop()` first would leave the OLD repo's watcher running forever, indefinitely mixing its future live events into the new repo's message state. Fixed by extracting the shared catch-up-then-watch sequence into `activateRepo(repoPath)` (used by both initial boot and by a new `workspace:switch` channel), with `messagesByFile.clear()` before reseeding — a different repo's files have nothing in common with the old ones, even coincidentally.

### 95. Gap 2, verified the hard way: stubbing a real OS dialog, not skipping the check
Playwright cannot drive a native OS folder-picker (it's outside the web page entirely) — solved by using `electronApp.evaluate()` to monkey-patch `dialog.showOpenDialog` directly inside the real running main process, immediately before clicking the real "Switch repository" button, so the actual `workspace:switch` handler and the actual `activateRepo` logic ran unmodified. Built two separate real git repos and drove the full sequence: confirmed the file list, active-repo-path display, and messages all correctly flipped to the new repo — and, critically, that editing the OLD repo's file *after* switching produced no live message at all (proving the old watcher was genuinely stopped, not just ignored), while editing the NEW repo's file correctly produced a fresh live message.

### 96. Gap 3: per-file status needed no new IPC channel at all
The third gap ("show this file's current drift status, not just the repo-wide list") looked at first like it would need a new `messages:getForFile` pull channel. It didn't: main already pushes the FULL current snapshot on every live event (the Objective 3.15 design). The fix lives entirely in the renderer — keep the latest pushed snapshot in a client-side variable (`latestMessages`), and filter it by `relativePath === currentRelativePath` into a new per-file status line, refreshed on file-open and on every live event. Zero new backend surface, because the correct data was already being delivered; it just wasn't being kept anywhere.

### 97. Verified end-to-end: cross-file leakage is the failure mode that matters here
Built a two-file repo, each file with its own undocumented function. Opening one file showed only its own message in the new file-status line, while the repo-wide panel correctly showed both (also incidentally re-confirming Objective 3.15 §84's `relativePath`-keyed dedup fix, since both files' messages happen to have byte-identical text). Editing the OTHER file externally while the first stayed open changed the repo-wide panel but left the open file's status line untouched — the one failure mode that would have actually mattered if the filtering logic were wrong.

### 98. Full suite unaffected, by design
All three fixes lived entirely in `electron/*` — none touched `src/`, so the Jest suite's 88/88 was unaffected by any of them and re-run only as hygiene, not because logic under test had changed.

## Recurring patterns, continued from Phase 1 & 2

6. **Reuse proven mechanisms instead of rebuilding them, a fourth and fifth time** — git's own rename detection and merge/conflict/branch-protection system were both chosen over custom-built equivalents, for the same reason SHA-256 was chosen over a hand-rolled hash function in Phase 1.
7. **Eliminate a category of bugs by construction, don't just carefully avoid them** — choosing a local desktop architecture over a distributed agent-plus-server design removes an entire class of network/distributed-systems failure modes structurally, rather than defending against them individually.
8. **Match tools to real, current project needs — not to an earlier plan or a desire to use them** — MySQL/MongoDB/RabbitMQ/GraphQL-WebSockets were dropped from the tool itself once their actual justification (multi-user, always-on, remote) stopped applying, with a genuine, separate place identified for the technologies that were dropped, rather than forcing them in or discarding the learning value entirely.
9. **Question infrastructure cost as part of correctness, not just architecture** — recognizing that required paid/hosted infrastructure creates a real access barrier was as important to the final decision as the technical complexity/bug-surface arguments.
10. **When a fix doesn't work, shrink the problem instead of guessing harder** — the Electron `app`/`BrowserWindow` bug wasn't solved by trying more fixes at the same scale; it was solved by writing a two-line probe script and reading a source file directly, which turned a vague "the API is missing" into a precise, checkable fact (`process.type` should be `"browser"`, and it wasn't).
11. **A generic error is a prompt to get closer to the source, not a prompt to guess** — "Process failed to launch!" and "Cannot read properties of undefined" both looked like dead ends until traced to their actual origin (raw `electron.exe` invocation, then `node_modules/electron/index.js`'s real source, then the shell's own environment variables).
12. **A per-machine bookmark is not the same category of data as shared content, even when it's convenient to store them side by side** — the last-synced-commit pointer looked at first like it belonged next to the documentation records it helps process; it doesn't, because one is genuinely shared and one genuinely isn't, and conflating them was a real bug, not just an untidy choice.
13. **State a limitation's actual severity separately from whether it can be fixed** — "unfixable" and "catastrophic" got bundled together in the first pass on the rename-threshold floor; they're independent questions, and the second one turned out to depend entirely on a different, still-open decision (the deletion handler) rather than on the unfixable part at all.
14. **Prove a mechanism's real behavior with a standalone probe before building on top of it, even for a well-known library** — chokidar's actual event ordering (add-before-unlink) contradicted the lower-level `fs.watch` result measured on the very same machine minutes earlier; assuming one would generalize to the other would have shipped a backwards design.
15. **A test still failing after a fix doesn't mean the fix was wrong** — three tests stayed red even after correcting the event-ordering assumption; adding real instrumentation to the actual code, rather than guessing at further fixes, revealed the tests themselves had an unrelated timing bug.
16. **A manual escape hatch is the correct answer to a proven-permanent automatic limit, not a fallback of last resort** — once zero-shared-lines renames and the app-closed gap were both established as genuinely undetectable by any cleverer heuristic, building a human-verified recovery path was the actually-correct fix, not a consolation feature bolted on afterward.
17. **Demonstrating a principle for someone else can find bugs the principle's own author never hit** — building a concrete example to answer "does this actually work" surfaced a real, previously-undiscovered gap (the empty cache for pre-existing files) that every prior test had happened not to exercise, simply because every prior test's fixture file was created *after* the watcher started.
18. **A confident, well-reasoned prediction about a module-system boundary still needs testing, not trusting** — expected the CommonJS-down-leveled dynamic import to fail against a real ES module at runtime; it didn't. The CJS/ESM boundary in this project has produced enough genuine surprises (the Electron shell saga alone) that "this should fail" deserved the same real-execution check as "this should work" always got.
19. **The very first real end-to-end test is often where integration bugs hide, not unit-level ones** — every piece involved (WorkspaceService, SyncService, LiveWatchService) was already individually tested and correct; the shared-userData-folder bug, the message duplication, and the crash-safety gap only surfaced once they ran together, for real, inside the actual Electron process.
20. **A component "working and rigorously tested" is a claim about the code that existed when it was tested, not blanket immunity from being the cause of a new symptom — but the correct response is to check it, not to skip past it either way.** When `findDocumentedNodes` returned a too-wide selection, the fastest-looking next step was to suspect `writeDoc`, since that's where the record is actually built. Reading the real stored JSON off disk first — rather than assuming either "writeDoc is proven, so look elsewhere" or "something must be wrong somewhere in the write path" — settled the question with one piece of direct evidence instead of a guess in either direction, and pointed straight at the actual, narrower bug.
21. **"Does the app do everything the user wants" is answered by grepping the actual wiring, not by re-deriving it from the design discussion that came before.** A three-mode UI design had just been agreed on, reasoning correctly about which *services* existed -- but that discussion never asked whether a given service *method* had ever actually been connected to a button. Explicitly reversing course from a plausible-sounding answer ("yes, we have everything") to an evidence-based one (grep every service method against `main.ts`, `preload.ts`, and `index.html`'s real call sites) found three real gaps a design-level review had no way to see, including one where the app's own error message pointed at a feature that didn't exist.
22. **An exclusion check on a shared ancestor (`if (event.target.closest(".x")) return`) is a fragile substitute for structural separation, not an equivalent to it.** A single click listener on a whole row, carved out for one sub-element, looked correct and had worked fine -- until unrelated changes (wider buttons from added icon text) silently broke it, because the guard depends on exactly where a click lands relative to a sibling's current size, not on anything actually structural. Moving the listener onto the specific content element instead made the two interactions structurally incapable of colliding, independent of any future size change -- found only because the real click was tested (`getBoundingClientRect()` on both elements), not because the exclusion logic was re-read and judged correct on paper.

## Objective 3.18 — Monaco, Two Themes, and a Real Color System

### 99. Doing the highest-leverage visual thing first, not last
Asked directly how to make the app look like the polished desktop apps it was being compared to (VSCode, Docker Desktop, Spotify). The recommendation, and the reasoning behind it: the code display is the visual centerpiece of the whole app, and swapping in Monaco would end up dictating a lot of the surrounding layout on its own (gutter, line numbers, font metrics) -- doing a cosmetic pass on the plain-textarea layout first, then swapping Monaco in after, would mean redesigning the content pane twice. Monaco went first, before the 3-mode structural split and before any broader visual pass.

### 100. Verifying the actual shipped file layout before writing a worker config from memory
`monaco-editor` 0.56.0's `min/vs` folder looks different from older versions at a glance (hashed bundle filenames like `css-CaeNmE3S.js` suggest a newer, possibly Vite-based build pipeline) -- rather than trust a remembered classic `MonacoEnvironment.getWorkerUrl` snippet against this specific version, `find node_modules/monaco-editor/min/vs -iname "*worker*"` was run first. It confirmed the classic per-language worker paths (`vs/editor/editor.worker.js`, `vs/language/typescript/ts.worker.js`, etc.) still exist alongside the newer hashed ones, meaning the standard non-bundler AMD-loader recipe was still valid for this exact version -- checked, not assumed, before being relied on.

### 101. Two boundaries that had to be bridged, not eliminated
No bundler exists in this project (electron/index.html is a static file loaded via `window.loadFile`), so Monaco was integrated via its documented non-webpack path: `monaco-editor/min/vs` copied into `electron/dist/vs` as an extra step in `build:electron`, loaded via its own AMD `loader.js` directly in the page. Separately, every backend call (`writeDoc`, `findDocumentedNodes`, `attachArchivedRecord`) works in raw character offsets, while Monaco's entire API works in `{line, column}` positions -- bridged with `model.getOffsetAt()`/`model.getPositionAt()` in exactly two small functions (`getSelectionOffsets`, `selectByOffsets`), with zero backend changes, since the offset contract itself never needed to change, only what translates to and from it in the UI.

### 102. The fidelity gap flagged back in §69/§89 is genuinely closed now
The plain `<textarea>` could never color a character range within its own displayed text -- the reason the documented-sections list panel existed as a workaround in the first place, and the reason "click a highlighted region" had to be clarified earlier as "click its row in the side list," not a click on the code itself. `editor.deltaDecorations()` now paints a real background tint over every documented span, and `editor.onMouseDown` (converting the click's position to an offset and checking it against the current documented ranges) makes clicking directly on that highlighted code jump to it -- the side list still exists as a navigable index, but it's no longer the *only* way to reach a documented region.

### 103. Verified via round-trip, not by reading the selection back directly
Monaco's internal editor/model instances are closure-local to the `main()` callback, not exposed on `window` -- rather than pollute the shipped page with debug hooks to peek at them directly, the offset↔position bridge was verified through an existing, already-meaningful side effect: `writeDoc` deliberately throws a specific error (with the original `recordId` embedded in its message) when a selection exactly matches an existing record. After documenting a function, clicking its documented-sections row, then attempting to write again, produced that EXACT error with the ORIGINAL recordId -- proving the round trip (`selectByOffsets` → Monaco's internal selection → `getSelectionOffsets` reading it back) was byte-exact, since any drift at all would have produced either no error or a different, wrong recordId. The same test repeated by clicking directly on the real rendered decoration element (its actual `getBoundingClientRect()`, not a guessed pixel position) confirmed the new inline-click affordance was equally exact.

### 104. Two real themes, one shared source of truth, not two parallel designs
CSS custom properties (`--bg`, `--fg`, `--blue`, `--green`, `--red`, `--red-light`, etc.) defined once under `:root` (light) and overridden under `[data-theme="dark"]`, toggled on `<html>`, cover every piece of the app's own chrome. Monaco needed its own parallel mechanism (`monaco.editor.defineTheme` building on its built-in `vs`/`vs-dark` bases, switched via `monaco.editor.setTheme`) since it renders independently of the surrounding page's CSS -- both are driven by the same single toggle function, so the editor and the chrome around it can never fall out of sync with each other. Persisted via `localStorage`, deliberately not through `WorkspaceService`: this is a per-machine UI preference, not repo data, and doesn't belong anywhere near the cross-machine-consistent storage design from Objective 3.10.

### 105. The red/green/blue system, and the one real ambiguity in it
Mapped: green = documented/success (the new inline decorations, "Documented"/"Attached" confirmations), red = destructive/error (Delete, Discard, error-severity messages), blue = informational/primary (info-severity messages, primary action buttons, the active-file indicator). The one real ambiguity -- the existing `warning` severity used amber, which isn't a variant of any of the three -- was resolved deliberately rather than picked by default: a distinct, lighter/orange-leaning red tint, keeping strictly to the three-hue system while still reading as "same family as error, less severe" rather than identical to it.

### 106. Verified with real evidence, including one honestly unplanned confirmation
Drove the real Electron app end-to-end: Monaco mounted and rendered actual file content with zero console/page errors (confirming the worker setup was correct, not just silent); decorations existed as real DOM elements, not merely "no exception was thrown"; both round-trip tests (§103) passed with exact recordId matches; the theme toggle was confirmed to change BOTH the CSS chrome (`document.body`'s computed background) AND Monaco's own editor background color, checked independently. One thing surfaced without being deliberately tested for: running a later verification script picked up the dark-mode choice from a previous, separate app launch via `localStorage` -- unplanned, but real evidence the persistence mechanism genuinely survives across restarts, not just within one session.

### 107. What's left
The 3-mode structural split (Dashboard / Code+Docs / Archive as distinct views with navigation, rather than everything on one crammed screen) is the one deferred piece left from the "what should we do to look professional" conversation -- Monaco was deliberately done first because it would have reshaped that structure's centerpiece anyway.

## Objective 3.19 — Splitting the Renderer, the Nav-Rail Restructure, and a Real Layout Bug Found by Testing

### 108. Splitting `index.html` was a real question, not a rhetorical one
Asked directly whether Electron even allows separating markup, styles, and script into their own files, or whether the single-file structure was some tool limitation. Neither: Electron's renderer is an ordinary Chromium page, so `<link rel="stylesheet">` and `<script src="...">` work exactly as in any webpage -- the single file was purely an incremental-build choice from early on, never a constraint. Split into `index.html` (markup), `styles.css`, and `renderer.js`, with a new `electron/copy-assets.js` replacing the growing chain of inline `node -e` copy commands in `build:electron` -- itself a small instance of recurring pattern #2 (the stale-`index.html` bug from Objective 3.13 was exactly this class of problem, solved the same way again: an explicit, un-skippable copy step).

### 109. One real CJS/ESM boundary surprise, caught immediately by running it
`copy-assets.js` was first written with `import` (ESM), consistent with the rest of the project's `"type": "module"` root `package.json` -- and immediately failed with `SyntaxError: Cannot use import statement outside a module`. `electron/package.json` (`{ "type": "commonjs" }`) overrides the root setting for everything under `electron/`, the same deliberate CJS/ESM boundary documented back in Objective 3.3/3.13 for `main.ts`/`preload.ts`. Fixed by writing it as CommonJS (`require`), matching the island it actually lives in -- caught in seconds by just running the build, not by re-deriving the module boundary from memory.

### 110. The nav rail: reframing the 3-mode split as navigation, not new panels
Dashboard / Code+Docs / Archive became three `.view` containers, exactly one visible at a time, switched via a narrow icon rail (`.nav-item` buttons) modeled on VSCode's activity bar -- Messages moved out of a cramped 160px strip at the bottom of every screen into Dashboard's full-height main content; Archive's browse/attach panel got the same full-width treatment. No new capability was added here at all -- every underlying function (`loadFileList`, `refreshDocumentedSections`, `refreshArchiveList`, `loadCatchUpMessages`) was reused completely unchanged; only the surrounding markup and a `switchView()` function calling `classList.toggle("active", ...)` were new.

### 111. Monaco inside a view that can become `display:none` needed one deliberate decision
Hiding a container collapses it to 0×0, and Monaco has real, documented trouble recovering from being created inside a zero-size container. Rather than risk it, Code+Docs was made the DEFAULT active view specifically so Monaco is always created while genuinely visible -- and `switchView("code")` explicitly calls `editor.layout()` on activation, rather than trusting `automaticLayout`'s polling to catch a hide→show cycle on its own timing. Verified directly, not assumed: after a full dashboard→archive→code round trip, Monaco's real rendered width was checked (734px, not 0) and its content was confirmed still displayed.

### 112. A real bug found by testing the actual click, not by testing that a function ran
The first full run of the restructured UI failed at exactly one point: re-selecting a documented row after adding icon+text to its Edit/Delete buttons, then attempting a duplicate write, silently got "Select some code in the file above first" instead of the expected duplicate-record error. Diagnosed with real evidence, not a guess: reading the row's and its `.row-actions`' actual `getBoundingClientRect()` values showed the row's geometric center now fell *inside* the actions button area (`centerIsInsideActions: true`) -- the wider icon+text buttons pushed the action bar's footprint wide enough that a short row's natural center landed on it. The first fix attempt (floated → flexbox layout for the header) changed nothing, because the real cause wasn't the CSS positioning method at all -- it was that ANY top-positioned action bar on a short row will tend to overlap that row's geometric center, regardless of how it's laid out.

### 113. The actual fix: attach the interaction to content, not to a shared ancestor with an exclusion check
The original pattern -- one click listener on the whole row, with `if (event.target.closest(".row-actions")) return` -- looked correct but wasn't robust: it depends on exactly where a click lands relative to a sibling element's current size, which can silently break the next time button padding, font size, or content changes. The real fix moves the "select this row" listener onto the `.lines` label and `.text` body specifically (and the equivalent `.origin`/`.text` for archive rows) -- structurally disjoint from `.row-actions`, so it is no longer *possible* for the two interactions to collide, independent of any future width or height change. Applied to both the documented-sections row and the archive row, since both shared the identical original pattern and the identical latent risk.

### 114. Monaco's own theme, tuned rather than left at stock defaults
`rapid-docs-light`/`rapid-docs-dark` gained real `colors` overrides (background, gutter, line numbers, cursor, selection) using the same hex values already defined in `styles.css` -- restrained deliberately to UI chrome, not a full custom syntax palette, since Monaco can't read CSS custom properties at all (a real, permanent seam between the two theming systems, kept in sync by hand) and rewriting token colors risked looking worse than Monaco's already-well-tested defaults for very little coordination gain.

### 115. Verified end-to-end, including the exact bug that had just been found
Rebuilt and reran the full sequence against a clean repo: default view is Code+Docs; icons render as real SVG elements; `writeDoc` and the documented-sections round trip still work; switching to Dashboard and Archive shows their content with Code+Docs correctly hidden; switching back gives Monaco a real, non-zero width; the row-click round-trip (via the corrected `.text` target) now matches the original `recordId` exactly; Monaco's own background color switches correctly with the theme toggle. Zero console/page errors throughout. Full Jest suite unaffected (88/88), since none of this touched `src/`.

### 116. What's left
Nothing outstanding from the "make it look professional" conversation -- Monaco, the nav-rail restructure, the icon set, the spacing/typography scale, and Monaco's coordinated theme colors are all in place and verified. Any further visual refinement from here is genuinely optional polish, not a gap.

## Objective 3.20 — The First Real Bugs Found by Actual Human Testing

### 117. A whole new testing phase, and it found something automated testing never could
Manual end-to-end testing began: a real GitHub repo, two real GitHub accounts acting as two collaborators, working through a full checklist (`TEST-CHECKLIST.md`) by hand rather than through any scripted test. The very first real action -- launching the app, then pointing "Switch repository" at a real, freshly-created git repo -- crashed the app immediately. No automated test in this entire project had ever exercised this, because every prior test fixture (in both Jest and the many scratch Playwright scripts) always committed at least one file before ever calling `sync()`. A completely normal real-world state -- a brand-new repo with zero commits -- had simply never been tried.

### 118. Bug 1: `git rev-parse HEAD` crashes on a repo with no commits, and nothing caught it
`GitService.getHeadCommit()` ran `git rev-parse HEAD` and let it throw on failure, unmodified since Phase 1. A repo with a real `.git` folder but zero commits (fresh `git init`, or a brand-new empty GitHub repo before the first commit -- exactly what was being tested) makes this command exit 128 with "unknown revision." The exception propagated all the way up through `SyncService.sync()` and `activateRepo()`, crashing the whole Electron app. Fixed by having `getHeadCommit` catch specifically that failure (matched against the real observed stderr text, not guessed) and return `null` -- the same "nothing yet" convention `getLastSyncedCommit` already used -- and having `sync()` treat a null HEAD as "nothing to sync yet," returning immediately without touching the sync pointer. A zero-commit repo is a legitimate state to work with, not an error to reject.

### 119. Bug 2: the very question that prompted this -- "is there a check for git repos?"
There was, but inconsistently: `workspace:switch` validated the chosen folder had a `.git` directory; the very first launch's `determineRepoPath` validated nothing at all when a fresh folder was picked (only its "recall the last repo" branch checked). Unified into one shared `isGitRepo()` helper used by both paths. `determineRepoPath` now loops back to the picker with a clear native error box (`dialog.showErrorBox`) instead of silently accepting a non-repo folder; `workspace:switch`'s existing thrown error, which the renderer had never actually caught (an unhandled promise rejection with zero visible feedback), now surfaces in a small status line next to the button.

### 120. Verified by reproducing the exact real scenario, not a simplified stand-in
Built the same two folders a real user would encounter -- a plain non-git folder, and a `git init`-ed repo with genuinely zero commits -- and drove the real app through both `workspace:switch` paths (native dialogs stubbed via Playwright's `electronApp.evaluate()`, same technique proven in Objective 3.15). Picking the non-git folder now shows the exact clear error message; switching to the empty repo succeeds with no crash, an empty file list, and "Nothing to report" on the Dashboard -- confirmed by actually reading the rendered DOM, not by the promise merely resolving. The one real hazard while doing this: the manual tester's own `preferences.json` (pointing at their real in-progress test repo) was sitting in the same location this verification needed to touch -- backed up before the test and restored immediately after, so the tester's own session picked back up exactly where they left it.

### 121. Regression tests added at both layers
`git.service.spec.ts`: a real repo with zero commits confirms `getHeadCommit()` returns `null` rather than throwing. `sync.service.spec.ts`: confirms `sync()` on such a repo returns `{ messages: [] }` without throwing, does NOT record a sync pointer, and that the normal first-time full scan still runs correctly once a first commit is later made (proving the fix doesn't just suppress the crash, it preserves the exact right behavior once real history exists). Full suite: 91/91 (88 + 3 new).

## Objective 3.21 — A Deliberate Scope Boundary, and Three Small UX Fixes

### 122. A screenshot of Electron's own default menu prompted a real scope conversation
Asked whether the File/Edit/View/Window bar visible in a screenshot was something built, or Electron's own doing. It was entirely Electron's automatic default (`Menu.setApplicationMenu()` had never been called) -- generic, mostly irrelevant boilerplate (Undo/Redo against a read-only editor, DevTools, zoom) that read as an unbranded prototype. This led directly into the user stating a deliberate, explicit product boundary: rapid-docs is not meant to become VSCode-like, should not grow file creation or content-editing capabilities, and exists specifically to document code -- not to replace the editor someone already uses for writing it.

### 123. The boundary matches architecture that already existed, it isn't a new constraint
This isn't a late-breaking restriction -- `LiveWatchService` was built from early in the project specifically to watch for changes made through *any* external tool, so that rapid-docs never has to be the place code gets written. The user's stated boundary just makes explicit what the sync/reconcile/live-watch design had already assumed structurally. ## Objective 3.23 — Names in Messages, and a Layout Bug the Screenshot Made Obvious

### 136. A screenshot surfaced two genuinely different problems at once
A real screenshot of the per-file status area showed two things worth separating: the message text itself only ever said a node's TYPE and line number ("A ExportNamedDeclaration near line 7"), never its actual name -- and, independently, seven stacked messages for one file pushed the code editor almost entirely out of view. ### 137. The layout bug: unbounded growth where the Dashboard already knew better
`#file-status` had never been given a height cap -- `#messages-panel` (the Dashboard's repo-wide equivalent) already had one from when it was first built. A one-line CSS fix (`max-height: 140px; overflow-y: auto;`) brought it in line with the pattern that already existed one view over.

### 138. The names feature: the data was always there, just discarded on the way to the message
`RawFoundNode.node` (the raw underlying AST node) has everything needed -- a `FunctionDeclaration`'s `.id.name`, a `VariableDeclarator`'s `.id.name`, and so on -- but `checkFile` stripped every node down to `{ type, start, end, loc }` before it ever reached `generateMessages`, discarding the raw node and anything extractable from it. Raised it directly as a real, connected design question rather than silently deciding either way. The answer was to keep the current behavior: comments stay flagged like any other undocumented node, `extractName` correctly returns `null` for them (a comment has no name concept at all), and they fall back to the same generic phrasing everything else without a name gets.

### 140. Verified with real evidence covering both the extraction logic and its full path to the UI
Two layers of tests: `AstService.extractName` tested directly against real parsed code (not hand-built fake nodes) for every covered node type, plus the two edge cases that matter most -- an anonymous function (`null`) and a real comment node (`null`, doubling as proof comments genuinely do end up in `walkAllNodes` via `leadingComments`/`trailingComments`, not assumed). `DocumentationService`'s message generation tested separately for the exact resulting text, both the named and generic-fallback cases. ## Objective 3.24 — The Currently-Open File's Content Didn't Refresh Live Either

### 141. The same category of gap as the file-tree bug, found the same way
Reported plainly: editing a file in an external editor while that exact file was open in rapid-docs never updated what Monaco showed, until clicking away to another file and back. This is structurally the same class of bug as Objective 3.19's file-tree gap (`LiveWatchService` detects the change correctly; nothing on the renderer side acts on it for this specific piece of UI) -- but for the editor's actual content rather than the file list.

### 142. Why `messages` alone can't be the signal for "this file's content changed"
The obvious-looking fix -- refresh the open file whenever a live message arrives about it -- doesn't work, because a real content change can legitimately produce ZERO messages (the edit made the file fully clean, or it was already undocumented and stayed that way). A renderer only watching message content would see nothing and correctly conclude nothing needs refreshing, even though the file on disk just changed. `relativePaths` -- the list `LiveWatchService` already emits alongside `messages`, previously used only internally in `main.ts` to update the message map -- is the one always-reliable signal: it names exactly which file(s) were just re-checked, independent of what checking them found. Added a second, dedicated IPC push (`files:changed`) carrying just that list, deliberately separate from `messages:live` rather than overloading it.

### 143. The fix reuses the user's own manual workaround, doesn't invent a new refresh path
`onFilesChanged` in the renderer checks whether the currently open file is in the changed list, and if so, calls `openFile(currentRelativePath)` again -- exactly what clicking away and back already did manually, now automatic. Deliberately not a lighter-weight "just patch the content in place" alternative: `openFile` already correctly handles the model, decorations, documented-sections, and file-status together as one unit, and re-deriving a narrower path risked missing one of those. Guarded with a try/catch, since the file could have been renamed or deleted in the same moment `readFile` would throw for; in that case, the next live event's `loadFileList()` call (Objective 3.19) already keeps the file tree honest on its own.

### 144. Verified against both the reported scenario and the risk of overreacting to it
Reproduced the exact bug first: opened a file, edited it externally without ever clicking away, confirmed Monaco updated on its own. Then confirmed the fix doesn't overreact -- editing a completely unrelated file while a different one was open left the open file's view untouched, proven by checking `current-file` stayed the same rather than assuming a lack of visible error meant it was fine. Full suite unaffected (103/103), since this change lives entirely in `electron/`.

A screenshot of Monaco's built-in right-click menu (Go to Definition, Go to References, Peek, Command Palette) showed the same category of problem as the removed default title-bar menu back in Objective 3.21: functionality that assumes a full language server, none of which applies to a read-only viewer with no LSP behind it. ## Objective 3.26 — Four Real Issues From One Round of Use, and a Genuine Selection Bug

### 149. A leaking implementation detail, and a UI element that didn't fit its own content
Two small, related complaints from actually using the new confirmation message: the success text showed a raw recordId (`"Documented (recordId d694176f...)."`) -- meaningless to anyone who isn't reading the storage format directly -- and the doc-text field was a single-line `<input>`, cramped for what real documentation actually looks like (a sentence or more, sometimes multiple). Fixed both together: swapped the input for a multi-line, resizable `<textarea>`, and simplified the success message to `"Documented."`, auto-clearing after 3 seconds via a small reusable `setStatus(el, text, autoClearMs)` helper -- deliberately only for success messages; validation and error messages still persist until addressed, since those need to stay visible until the user actually does something about them.

### 150. The real bug: documenting a parent silently made its children unselectable
Reported precisely: right-clicking to select a piece of code that was a CHILD of an already-documented PARENT region kept selecting the parent instead, making it impossible to act on (edit, delete, copy, or separately document) just the child. Root cause: `onMouseDown`'s decoration-jump logic (added back in the Monaco integration, Objective 3.18) fired unconditionally on every mousedown, snapping the selection to the containing documented region's full bounds -- including at the very START of a drag. Any attempt to drag-select a smaller region nested inside a larger documented one had its starting point hijacked before the drag could even begin.

### 151. The fix: only snap on a plain click, and prefer the smallest match when several overlap
Moved the logic from `onMouseDown` to `onMouseUp`, gated on `selection.isEmpty()` -- only a genuine plain click (no resulting selection) triggers the "jump to the documented region here" convenience behavior now; any real drag, even one entirely inside a documented parent, is left exactly as the user made it. A second, related bug fixed at the same time: when a click point falls inside MULTIPLE overlapping documented regions (a parent and a child both independently documented -- `writeDoc` has never prevented this, since overlapping selections just produce different recordIds), the old code picked whichever happened to come first in an unordered list. Now picks the smallest (most specific/innermost) match, which is almost always what a click at that exact point actually means. Right-click continues to work correctly through this same path, since mouseup still fires before contextmenu in the real event order (mousedown → mouseup → contextmenu), confirmed directly rather than assumed.

### 152. A second real bug found while verifying the first: Escape silently did nothing
Added a "dismiss the context menu on Escape" handler as a fourth, smaller fix -- and it didn't work, the menu just stayed open. Diagnosed with real evidence, not a guess: a raw `keydown` listener on `document` registered with `{ capture: true }` DID see the Escape key; the app's own listener, registered on the default bubble phase, did not. Monaco's own internal keyboard handling (on its hidden `native-edit-context` element, confirmed as the actual focused element at the time) calls `stopPropagation()` on Escape as part of its own behavior, which meant a bubble-phase listener on `document` never received the event at all whenever the editor had focus -- which is effectively always, right after a click or drag. Fixed by registering the dismiss handler on the capture phase instead, intercepting the key before Monaco's own handling gets a chance to stop it from propagating.

### 153. Verified end-to-end, all four fixes together, in one real session
Real repo, a function containing a nested if-block, both independently documentable: confirmed the doc-text field is a real `<textarea>`; confirmed a genuine write through the actual UI (drag-select, type, click) shows `"Documented."` with no recordId, and confirmed it auto-clears a few seconds later. Documented the whole outer function, then drag-selected just the inner if-block (a real child of that now-documented parent) and right-clicked it -- confirmed the menu correctly offered `"Document selection"`, not `"Edit documentation"`, proving the selection was never silently hijacked to the parent's bounds. Pressed Escape with the menu open and confirmed it actually closed, after fixing the capture-phase gap found in the same verification pass. Full suite unaffected (103/103), since none of this touched `src/`.

## Objective 3.28 — The Real Root of the Selection Bug, and Errors Written for Rapid-docs' Own Developers Instead of Its Users

### 158. A screenshot that looked like the earlier fix hadn't landed, but was actually a different, deeper bug
The tester reported the exact scenario Objective 3.26 had supposedly fixed -- right-clicking a documented child inside a documented parent still showed "Document selection" instead of "Edit documentation" -- and then hit the "already documented" error trying to write it, proving a record for that exact selection genuinely existed. Two parts of the app disagreed about the same selection: `writeDoc` recognized it as a duplicate; the context menu's own check didn't. That contradiction was the real signal something deeper than the mouseup/mousedown fix was wrong, not that the earlier fix had failed.

### 159. Reproduced with instrumentation before touching any code
Rather than theorize, a temporary debug hook was added to `getSelectionOffsets()` to capture the exact selection alongside `currentDocumentedSections` at the moment a context menu opened, and a minimal, controlled repro (a function with a nested if-block, structurally identical to the tester's real file -- confirmed by the resulting recordId hash matching the tester's screenshot byte-for-byte, real evidence the repro was the same underlying case) was driven through a real drag-select. The captured numbers: actual selection `{start: 52, end: 85}`, the stored record's reported boundary `{start: 54, end: 85}` -- off by exactly 2, the width of the if-block's leading indentation.

### 160. The actual root cause: two different definitions of "matches," and only one of them was ever correct
The context menu compared the current selection's offsets against `findDocumentedNodes`' reported start/end using strict equality. But `findDocumentedNodes` reports a *specific AST node's own natural boundary* -- and `writeDoc`'s own duplicate check has never worked that way: it recomputes `filterByHighlight` (deliberately contains-based, `entry.start >= highlightStart && entry.end <= highlightEnd`) over whatever the CURRENT selection actually is, and compares the resulting combined hash against storage. A real human drag almost never lands exactly on an AST node's first character -- it commonly starts a little early, on the leading whitespace/indent -- which `filterByHighlight` correctly treats as irrelevant (no AST node lives in pure whitespace) but strict position equality does not. This is the same category of bug as the original `findDocumentedNodes` fix all the way back in Objective 3.14: checking position instead of checking the actual structural computation.

### 161. The fix: give the UI the same authoritative check `writeDoc` already trusts, not a client-side position comparison
Extracted the shared hash computation out of `writeDoc` into `computeHighlightMembers()`, then added `DocumentationService.findRecordForSelection(repoPath, relativePath, highlightStart, highlightEnd)` -- runs the identical structural computation as a pure read, returning the matching record (if any) without writing anything. Wired through a new `docs:findRecordForSelection` IPC channel. The context menu's `contextmenu` handler became `async`, calling this instead of scanning `currentDocumentedSections` by position -- the two code paths (`writeDoc`'s duplicate check and the context menu's "does this match" check) can no longer disagree, because they are now, structurally, the same computation.

### 162. Verified against the exact reported scenario, both with and without the overlap
Reran the identical repro: right-clicking the documented if-block with NO parent documented yet now correctly shows Edit/Delete/Copy (previously it didn't, proving the bug wasn't really about parent/child overlap at all -- that was just the scenario that happened to surface it). Then documented the parent too, recreating the exact overlap from the report, and confirmed the same if-block STILL correctly shows Edit/Delete/Copy. Three new `DocumentationService` tests lock this in directly: a selection whose boundary is deliberately looser than the underlying node's exact position still resolves to the same record; a genuinely non-matching selection returns `null`; an unparseable file returns `null` rather than throwing.

### 163. Errors that were technically accurate and completely wrong for the audience reading them
Quoted directly: `"Error invoking remote method 'docs:writeDoc': Error: This exact highlight is already documented as record \"06d54082...\". Use editDocText to change its text instead."` -- Electron's own IPC wrapper boilerplate, a raw internal hash, and a reference to a method name (`editDocText`) that isn't even how the UI's own Edit button is reached. All plumbing for whoever is developing rapid-docs itself, none of it appropriate for whoever is using it. Added `friendlyErrorMessage()`: strips the IPC wrapper via one regex, then rephrases the one specific case worth naming ("already documented") into `"This is already documented. Use the Edit button to change its text."` -- anything unrecognized still falls back to the de-wrapped original rather than hiding the problem entirely. Applied at all three places a raw backend error had been shown directly: `write-doc-status`, `archive-attach-status`, and `switch-repo-status`.

### 164. Status messages that were visible in the DOM but still didn't look like they mattered
Beyond color (Objective 3.27), the tester specifically compared these unfavorably against the message-row boxes in Messages/Dashboard, which "look really cool." Extended `#write-doc-status`/`#archive-attach-status`/`#switch-repo-status` from colored text to small colored chips -- background plus text color together (`--red`/`--red-bg`, etc.), matching `.message-row`'s actual visual language instead of approximating it with color alone. Collapses to nothing (`:empty { display: none; }`) when there's no active message, rather than an empty box sitting in the layout.

### 165. Verified end-to-end: the friendly text and the real chip background together
Triggered the exact duplicate-record error through the real UI and read both the rendered text and the computed background color directly: `"This is already documented. Use the Edit button to change its text."`, with `background-color: rgb(251, 233, 231)` (`--red-bg` exactly) and `color: rgb(192, 57, 43)` (`--red` exactly). ## Objective 3.29 — Console Staining, Traced to Electron's Own Binary, Fixed the Same Way as the Git One

### 166. A stack trace the app itself never printed
Quoted directly: `"Error occurred in handler for 'docs:writeDoc': Error: This exact highlight is already documented..."`, with a full stack trace pointing into `dist/ast/documentation.service.js` and Electron's own internal `browser_init` bundle. The instruction was explicit and general: every error the tester would encounter during the rest of manual testing needed the same treatment already proven for the git stderr case (Objective 3.20 §131-132) -- not just this one instance.

### 167. Verified the source before touching anything, the same discipline as the git fix
`grep -rn "Error occurred in handler" node_modules/electron/` matched only inside `electron.exe` itself -- a compiled binary, not a JS file in `node_modules` that could be patched, monkey-patched, or intercepted through any documented Electron API. This is Electron's own `ipcMain.handle` internally logging any handler's rejection, unconditionally, with no public config flag to suppress it. Confirmed as a hard constraint before designing around it, not assumed.

### 168. The fix: never let a handler actually reject across the IPC boundary, for errors the app already handles correctly
Electron only logs when a handler throws or its returned promise rejects -- so the fix is to make every handler that can fail in an "expected" way (a duplicate record, a missing file, "no repo active") always RESOLVE instead, wrapping a caught error into a plain marker object (`{ __rapidDocsError: true, message }`) rather than let it propagate. `safeHandle()` (main.ts) is a thin wrapper around `ipcMain.handle` doing exactly this; `invokeOrThrow()` (preload.ts) is its counterpart, unwrapping that marker and throwing it again -- but as a plain, local, in-process JS exception that never touches Electron's IPC layer at all. Applied to every handler capable of throwing (`files:read`, all `docs:*` and `archive:*` write/read operations, `workspace:switch`, `workspace:close`); left untouched the handful that provably never throw (`ping`, `files:list`, `archive:list`, `messages:getCatchUp`, `workspace:getActiveRepoPath`).

### 169. Zero changes needed anywhere in renderer.js's own try/catch blocks
The whole point of re-throwing locally inside `invokeOrThrow`, rather than changing the return shape callers see: every existing `try { await window.rapidDocs.writeDoc(...) } catch (err) { ... }` block across the app keeps working completely unmodified -- `err` is still a real `Error`, still has a `.message`, still gets caught exactly where it always was. The fix is invisible from the call site's perspective; it only changes what happens at the IPC boundary in between.

### 170. A genuinely useful side effect: the error text itself got simpler too
`friendlyErrorMessage()`'s regex stripping Electron's `"Error invoking remote method 'X': Error: ..."` wrapper (Objective 3.28 §163) is now provably dead code -- confirmed by capturing the real error text after this fix and finding no wrapper present at all, since the message is now constructed directly from `result.message` rather than arriving via an actual rejected IPC call. Removed rather than left in defensively, with the removal itself justified by the same real evidence that motivated it.

### 171. Verified by capturing the actual main-process stdout/stderr, not by eyeballing a terminal
Reproduced the tester's exact scenario -- write a doc, then attempt the identical selection again -- through the real UI, this time with Playwright's `electronApp.process().stdout`/`.stderr` piped into a buffer for direct inspection (not page-level `console` events, the real OS-level process streams a human would actually see in their terminal). Confirmed the renderer still shows the correct friendly error, and confirmed the captured output contains no `"Error occurred in handler"` text anywhere. The remaining output is exclusively the app's own intentional `console.log` bootstrap messages and unrelated Chromium sandbox/GPU-cache noise specific to this test environment. Full suite: 106/106, unaffected since this is IPC plumbing, not business logic.

## Objective 3.30 — Problems vs. Activity: Two Kinds of Message, and a Hash-Collision Bug Found Twice in the Same Fix

### 172. Not every message can be "cleared" the same way, and that distinction had to be resolved before anything else
Real screenshots of the file-status panel and a request to make write-doc feedback persistent and batch-clearable, framed against VSCode's Problems/Output/Debug Console/Terminal tabs, looked at first like one feature. It's actually two, with genuinely different semantics: file-status messages are a LIVE, recomputed reflection of current repo truth -- clearing one doesn't fix the underlying problem, so it can legitimately reappear the moment the file is genuinely rechecked. The write-doc-button's feedback is a one-off EVENT, not a fact about the repo -- nothing ever recomputes it, so it can become a real, append-only, manually-clearable log. Named "Problems" (VSCode's own term for exactly this concept) and "Activity" respectively, and confirmed directly with the tester which distinction to keep: Problems stays clearable even knowing it can resurface, Activity is a real removal.

### 173. A real, verified gap: genuinely new code added to a stale record showed no message of its own
Before touching the UI, investigated a specific claim directly rather than assuming it was just a feature request: does adding brand-new code to an already-documented, now-partially-stale function surface anything specific about the addition, or only "the whole function has no documentation"? A controlled test (add a new `if` branch to a documented `fib()`) confirmed the latter -- `checkFile` correctly detects the new branch internally, but `collapseToTopLevel` swallows it, because the outer, now-stale `FunctionDeclaration` also technically fails the "is this hash documented" check and gets treated as a valid containing parent.

### 174. First attempt at the fix was wrong, caught before it shipped: comparing hashes from two different points in time
The first fix compared `driftResults[].changedMembers`' hashes against the current undocumented candidates' hashes to exclude "already-covered" containers -- and it did nothing, confirmed by rerunning the same investigation script after the change. The reason: `changedMembers[].hash` is, BY DEFINITION, the OLD hash from before the edit (that's what "changed" means) -- it can never equal a CURRENT node's hash, for anything that actually changed. Comparing them was comparing two different eras of the same node and expecting them to match.

### 175. Second attempt, correct in principle, broke on the exact same class of bug the project had already learned from once
The corrected approach: exclude a candidate if it structurally CONTAINS at least one node whose CURRENT hash matches something still documented (proof of genuine overlap with valid content, not a hash-era mismatch). Tested against the real fib() scenario -- and the genuinely new `if` branch vanished from `undocumentedNodes` entirely, not just its container. Direct evidence (printing every node's type, position, and hash) showed why: hashing is deliberately position-invariant, so the parameter `n` -- present in both the original code and the brand-new branch -- hashes identically everywhere it appears. The new branch's own `n` "matched" a documented hash purely by coincidence of reusing a common name, which was wrongly read as proof the whole branch overlapped old content. This is the exact same trap `findDocumentedNodes` fell into and was fixed for back in Objective 3.14 (individual/leaf hash matches are unreliable; only a complete, structural match means anything) -- rediscovered one level removed, in a different method, because the underlying cause (position-invariant hashing) is the same everywhere in this codebase.

### 176. The actual fix: only compound nodes count as proof of overlap
Restricted the containment check to exclude simple, atomic leaf types (`Identifier`, `NumericLiteral`, `StringLiteral`, `BooleanLiteral`, `NullLiteral`, `RegExpLiteral`, `BigIntLiteral`, `ThisExpression`) from serving as evidence -- a compound node (`BlockStatement`, `IfStatement`, `BinaryExpression`, etc.) folds in the hashes of everything it contains, so a coincidental full match is implausible; a bare identifier's match proves nothing. Re-verified against both real scenarios: the new `if` branch in fib() now correctly surfaces its own `"A IfStatement near line 5 has no documentation yet."`, while a pure rename (Objective 3.15-era `renamedCode` fixture) still correctly excludes the stale `FunctionDeclaration`/`BlockStatement` containers, leaving only the genuinely renamed leaf identifiers and the always-separate `const x`. Existing test expectations (`12` undocumented nodes, `2` info messages) were updated to the new, correct counts (`6` and `3`) -- the old numbers encoded the noisier, pre-fix behavior, not a deliberate contract.

### 177. The tabs: reusing exactly what each kind of data already was, not inventing new state
`renderFileStatus()` (Problems) gained a `clearedProblemKeys` Set, checked before rendering and reset on every `openFile()` (a fresh file view has nothing to have dismissed yet) -- deliberately NOT reset by unrelated live events elsewhere in the repo, only by a genuine recheck of the CURRENTLY open file (piggybacked on the existing `onFilesChanged` → `openFile()` path from Objective 3.24, which already knew exactly when that was true). Activity is a real array (`activityLog`), appended to by every Document Selection attempt via `addActivityEntry()`, persisting across file switches (it's a log of actions, not per-file truth) but cleared on a repo switch (a big enough context change that old activity no longer applies). Both tabs share one `renderClearableRows()` renderer (checkbox + severity chip) and one pair of Clear Selected/Clear All buttons, dispatched based on whichever tab is currently active -- checkboxes specifically because clearing was asked to be a batch operation (1 to n at once), never a single "x" per row.

### 178. Verified end-to-end: accumulation, non-disappearance, correct-vs-incorrect clearing, and the tab switch itself
Drove three separate Document Selection attempts (two hints, one real success) through the real UI and confirmed all three persisted as separate Activity entries -- including after waiting 4 seconds, longer than the OLD 3-second auto-clear this round removed entirely. Confirmed Clear Selected removes exactly the checked entry, Clear All empties the rest. Separately, for Problems: confirmed clearing empties the tab, confirmed it stays empty with nothing on disk changed, then made a real external edit to the same file and confirmed the problem legitimately reappeared -- exactly the behavior explicitly agreed to going in, not a bug. One smaller gap caught in the same round: the Activity tab's "No activity yet." empty state never rendered until the first real entry, since nothing called its render function at startup -- fixed by rendering it once during the app's initial bootstrap, same as every other panel already does. Full suite: 108/108 (106 + 2 new `generateMessages` regression tests for the new-code-vs-stale-container distinction).

## Objective 3.31 — Partial-Staleness Warnings Named a Docs Sentence Instead of the Code

### 179. "Fibonnaci prime documented" doesn't tell you where to look; "findPrimeFibonacciNaive" does
Two screenshots of real partial-staleness warnings quoted the record's stored `docText` as the subject -- e.g. `"Fibonnaci prime documented" is partially out of date...`. Direct instruction: when a real name for the underlying code exists, use THAT instead of the docText quote, exactly like the undocumented-node messages already do (Objective 3.27-era `extractName` naming) -- a docText fragment is prose written by whoever documented it, not something a person can search their editor for; the function/variable/class name is.

### 180. Why the record itself can't just be asked for a name
A `DriftResult` carries only `changedMembers` (old hashes) and a `recordId` -- no position information survives from when the doc was originally written, since positions shift on every edit and hashes are the only stable identity kept. A fully-stale record (100% of members changed) genuinely has nothing left to point at in the CURRENT file -- there is no correct name to derive, and the docText quote remains the only honest fallback for that case.

### 181. The fix: derive the name from whatever the record's UNCHANGED members still anchor to
For a partially-stale record, the members that DIDN'T change are still real, current AST nodes with real current positions (their hash still matches something in `hashedNodes`). Computing a bounding box across just those unchanged members' current start/end, then finding the smallest CURRENT node that (a) fully contains that box and (b) has a non-null `.name` from `extractName()`, gives the nearest correctly-scoped, human-locatable container -- typically the enclosing function or variable the whole record was originally about. Added `name: string | null` to `DriftResult`, computed once per record inside `checkFile` alongside `changedMembers`; `generateMessages`' `partially_stale` branch prefers `drift.name` (quoted) as the warning subject when present, falling back to the existing docText quote otherwise. The `fully_stale` branch is intentionally untouched -- there are no unchanged members to anchor from, so `name` is always `null` there, and the docText quote stays correct.

### 182. Caught a wrong first read of "unchanged" before it shipped
Initially wrote the anchor set as `record.members` themselves rather than only the ones whose hash still exists in `currentHashes` -- which would have included members that changed, defeating the entire point (their old position/identity is gone, so they can't anchor anything current). Corrected by explicitly filtering `record.members` down to only those hashes present in `currentHashes` before computing the bounding box, matching the same "unchanged means the hash still resolves to something real right now" definition `changedMembers` itself already uses one line above it.

### 183. Verified against both branches with real, direct execution -- not just reasoning
A script driving the actual compiled `documentation.service.js` against a fixture matching the user's own screenshot (`findPrimeFibonacciNaive`, docText `"Fibonnaci prime documented"`), edited internally (loop start value and multiplier changed, function/parameter untouched): confirmed `driftResults[0].name === "findPrimeFibonacciNaive"` and the resulting warning read `"findPrimeFibonacciNaive" is partially out of date -- ...`, no docText quote anywhere. Then replaced the entire file content (nothing structurally related survives): confirmed `name` came back `null` and the message correctly fell back to `"Fibonnaci prime documented" no longer matches any code in this file...`, proving the fallback path still works rather than silently breaking. Two new `DocumentationService` tests lock both cases in directly (`uses the record's current, real name as the warning subject...` / `falls back to the docText quote when a record is fully stale...`). Reverified the same two scenarios end-to-end in the real Electron app (a fresh git-initialized test repo, `preferences.json` swapped and restored around the run) via a Playwright-driven session -- the Problems tab showed the exact same real-name and fallback-quote text as the direct script run, confirming the fix holds all the way through `generateMessages` → IPC → renderer rendering, not just at the backend layer. Full suite: 110/110 (108 + 2 new).

### 184. Reported as still broken against the user's own real repo -- and it genuinely was
After all of the above shipped, the tester rebuilt and relaunched against their own long-running test repo and still saw the OLD docText-quote style warnings for two real records (`"Fibonnaci prime documented"`, `"Now documenting this properly"`), both tied to the same `findPrimeFibonacciNaive` function in `initial.ts`. Rather than assume a stale build or a launch mistake, checked directly: read the real `.rapid-docs/initial.ts.json` storage, then ran `checkFile` against the real current `initial.ts` through the compiled backend. Confirmed the discrepancy was real -- `drift.name` came back `null` for both records, not a caching or rebuild artifact.

### 185. Root cause: the exact same hashing trap, a third time, now found in production data instead of a hand-built fixture
Added temporary instrumentation reproducing `checkFile`'s own anchor computation to inspect the intermediate bounding box directly. Found: 36 unchanged member hashes resolved to 53 CURRENT nodes matching those hashes -- far more anchors than unchanged members, the tell that some hash was being reused. The two extremes of the bounding box were both `Identifier` nodes carrying the identical hash for `findPrimeFibonacciNaive` -- one being the function's own name, the other its call site 20 lines later (`const result = findPrimeFibonacciNaive(20);`). Hashing is position-invariant on purpose, so a function's own name and a separate call to that function are structurally two different leaf nodes with one identical hash. The bounding box, built from every node matching an unchanged hash with no restriction on node kind, stretched out to include that unrelated call site -- past the function's own closing brace -- so no node existed that could contain the whole box AND carry a name, and `name` fell back to `null`. This is the identical bug class already fixed twice before in this file: Objective 3.14 (`findDocumentedNodes`) and Objective 3.30 §175 (the "new code" containment check) -- both times, and now a third time, because a bare leaf's hash match is never reliable evidence on its own, only a compound node's full-subtree match is.

### 186. The fix: restrict anchors to compound nodes, exactly like the already-established containment check
Hoisted the existing `ATOMIC_LEAF_TYPES` set (previously defined further down, scoped only to the undocumented-node overlap check) to the top of `checkFile`, and added the same exclusion to the anchor-gathering step: `hashedNodes.filter((node) => unchangedHashesForRecord.has(node.hash) && !ATOMIC_LEAF_TYPES.has(node.type))`. A lone unchanged leaf is no longer treated as reliable evidence of where a record's content still lives -- only unchanged compound nodes (whose full-subtree hash match is implausible by coincidence) anchor the bounding box now. If that leaves zero anchors at all, `name` correctly stays `null`, same fallback behavior as a fully-stale record.

### 187. Verified directly against the exact real data that exposed the bug, not a fresh fixture
Reran the same real-repo diagnostic after the fix, calling the actual (rebuilt) `checkFile` rather than reproducing its logic by hand this time: both real records now correctly resolve `name: "findPrimeFibonacciNaive"`, and the Problems-tab-bound messages read `"findPrimeFibonacciNaive" is partially out of date -- ...` for both. Added a new regression test built around the exact failure shape (a function whose own name is separately reused at a call site later in the same file, edited internally without touching either occurrence of the name) -- fails against the pre-fix code, passes after. Full suite: 111/111 (110 + 1 new).

### 188. Aside: why the same function produced TWO separate warnings, not one
Also asked about, from the same real repo: `initial.ts` had two independent stored records for `findPrimeFibonacciNaive`, each with a different `docText` ("Fibonnaci prime documented" and "Now documenting this properly") and each reporting a different changed-count against the current code (11/63 and 5/63). Confirmed directly from the raw `.rapid-docs/initial.ts.json`: both records share the same FunctionDeclaration position and many identical interior member hashes, but their root FunctionDeclaration hashes differ -- proof they were captured as two separate `writeDoc` calls at two different points in the function's edit history, not one record somehow duplicated. `writeDoc` has never checked "does a DIFFERENT record already cover this same code" -- it only refuses an EXACT duplicate of the current selection (Objective 3.28's `findRecordForSelection`) -- so documenting the same function again after editing it (rather than editing the existing record's text) simply adds a second, independent record. Both are now checked against current code independently every time, hence two separate warnings. This is exactly the scenario the new delete feature (Objective 3.32) is for: once a stale/superseded record has been reviewed and is no longer wanted, it needs a real way to be removed -- previously there wasn't one, for a record whose code no longer exactly matches anything current.

## Objective 3.32 — A Real Way to Delete a Record That No Code Matches Anymore

### 189. A genuine gap, not just a UX polish request: there was no way to delete a stale record at all
Asked directly: since a partially- or fully-stale record is never auto-deleted (Objective 3.31 §184 confirmed this), and the tester now understood WHY these warnings can pile up (duplicate re-documentation, Objective 3.31 §188), should there be a way to actually delete one -- balanced against the real risk of accidentally deleting a record still worth keeping? Checked the existing delete path (`deleteSection`, wired to the context menu's "Delete documentation" item) before answering: it only ever becomes reachable via `findRecordForSelection`, which requires the CURRENT selection to be an exact structural match. A partially- or fully-stale record, by definition, no longer has an exact match anywhere -- so there was, in fact, no existing way to delete one at all. Not a missing convenience; a real gap.

### 190. The recommendation, and why the severity split is the right constraint, not a limitation
Proposed and the tester agreed: offer real deletion only for `error` (fully_stale) messages in the Problems tab, never for `warning` (partially_stale) ones. A fully-stale record has zero surviving code -- "nothing matches this anymore" is unambiguous, so deleting it can never destroy something still useful. A partially-stale record, by contrast, still has real, accurate, unchanged content (that's the entire premise of the warning) -- offering delete there would make "review and update" and "permanently discard" sit one click apart on exactly the record most likely to still matter. The tradeoff accepted going in: this means a stale duplicate that's merely partially stale (like the two `findPrimeFibonacciNaive` records above) can't be one-click deleted even once reviewed -- editing its text via the existing Edit flow, or waiting for it to drift into fully-stale, remains the only path. That's the deliberate cost of never risking an accidental loss of still-valid documentation.

### 191. The fix, in three layers: a fact the message needed to carry, an existing IPC path that needed to also refresh, and a UI gated on severity
`Message` gained `recordId: string | null` -- populated from `drift.recordId` for both `warning` and `partially_stale` messages (both already know their record), left `null` for undocumented-node `info` messages and the couple of other `Message`-producing call sites that were never about one specific record (`sync.service.ts`'s parse-failure fallback, `handleDeletedFile`'s archive notice). `renderClearableRows` (shared by both Problems and Activity) gained an optional `deleteAction` callback, rendering a real `danger`-styled Delete button only when the item's severity is `error` AND it carries a `recordId` -- `renderFileStatus` is the only caller that passes one; `renderActivityLog` doesn't, since Activity entries were never records to begin with. Reused the EXISTING `docs:deleteRecord` IPC channel and `DocumentationService.deleteRecord` rather than adding a new one.

### 192. A real, latent gap in the existing delete flow, only now exposed
Deleting a record never touches the source file on disk -- only the `.rapid-docs/*.json` storage -- so `LiveWatchService` (which only watches actual source files) has nothing to fire on afterward. This gap already existed in the original context-menu delete path too, just invisibly: that path only ever reaches an `unchanged` record (an exact match), and an `unchanged` record produces no Problems message in the first place, so there was never anything on-screen that needed to disappear. The new Problems-tab delete path is the first case where this actually matters. Fixed at the `docs:deleteRecord` IPC handler itself (not just the new call site), so both delete paths benefit: after deleting, it calls the same `SyncService.handleFileEvent` + `replaceFileMessages` + `messages:live` push that the real file watcher uses, reusing the one existing "how messages reach the renderer" path rather than inventing a second.

### 193. Verified end-to-end in the real Electron app, both the positive and negative case
A fresh scratch git repo (`preferences.json` swapped and restored around the run, as usual): documented a function, then fully replaced the file's content (fully_stale) -- confirmed the Problems row rendered with a real Delete button, clicking it removed the record from storage (`findDocumentedNodes` confirmed empty afterward, though it was already empty pre-delete since staleness already broke the exact-match requirement) AND the message vanished from Problems immediately, with no unrelated file edit needed to trigger the disappearance. Separately, re-documented the same function and made it only partially stale instead (a rename, matching the earlier `renamedCode` fixture) -- confirmed that row rendered with NO delete button at all, exactly per the severity-gated design. Full suite: 111/111, unaffected by the `Message.recordId` addition (no existing test asserted on the object shape excluding it).

## Objective 3.33 — The Same Hashing Trap, a Fourth Time, Now Inside the Core Status Classification Itself

### 194. A real repo file that stayed "partially stale" after being entirely rewritten
While using the new Delete feature, the tester noticed `catalogue/third_file.ts` -- whose two stored records were both originally about a `fibonacciNaive` recursion function, now completely replaced by unrelated Graph-utility code (`buildGraph`, `breadthFirstSearch`) -- still reported `partially_stale` (warning), not `fully_stale` (error). Asked directly rather than assumed: does this mean something in the old hash genuinely correlates with the new code, or is this another instance of the same collision problem? Checked with real evidence before answering: instrumented `checkFile` to print exactly which stored members were still "matching" and where. Both records showed only 2-3 out of 28-51 members surviving, and every single survivor was a bare `NumericLiteral` -- the digit `1` or `2` -- matching a current node that had nothing to do with the original Fibonacci code at all.

### 195. The same bug class as Objective 3.14, 3.30, and 3.31 -- but this time in the ORIGINAL, foundational computation
`changedMembers`/status classification (`unchanged`/`partially_stale`/`fully_stale`) has existed since Phase 1 and had never been touched by the previous two collision fixes, both of which only affected newer features (undocumented-node detection, name derivation). It has the identical flaw: `currentHashes.has(member.hash)` checks whether a hash exists ANYWHERE in the file, with no notion of position or context -- so a record for code that's genuinely, entirely gone can still show a stray "unchanged" leaf purely because a common digit, or (confirmed separately while investigating) a common type keyword like `: number`, happens to reappear somewhere unrelated.

### 196. A side question surfaced something more valuable than a quick patch: was "compound" real terminology, and was the leaf list even complete?
Asked directly whether "compound" vs. "leaf" was established CS terminology or something invented for this project. Answered honestly: the underlying concept (atomic/primitive vs. compound/composite data) is standard programming-language theory (the same distinction SICP draws), and maps onto the equally standard tree-theory terms leaf vs. internal node -- but the SPECIFIC list of which Babel AST node type names counted as leaves had been hand-typed for this project, not derived from anything authoritative. Checking that directly, using Babel's own `VISITOR_KEYS` metadata (the exact data `@babel/traverse` itself uses to decide which fields hold child nodes), turned up a real, confirmed gap: TypeScript's keyword-only type nodes (`TSNumberKeyword`, `TSStringKeyword`, `TSBooleanKeyword`, and siblings) have zero visitor keys -- true leaves, exactly as collision-prone as a bare `NumericLiteral` -- and were never in the hand-typed set at all.

### 197. `ATOMIC_LEAF_TYPES` is now derived from Babel's own metadata, with one deliberate, explained exception
Replaced the hand-maintained array with `Object.entries(VISITOR_KEYS).filter(([, keys]) => keys.length === 0)`, computed once at module scope and shared by every place in `documentation.service.ts` that needs it (previously, a near-identical Set was redefined inline inside `checkFile` itself -- collapsed to one definition). `Identifier` is added back in on top, deliberately: Babel's own metadata says it CAN technically hold children (an optional type annotation, decorators), so the strict "zero visitor keys" rule alone would have dropped it -- but for the overwhelming majority of real, untyped identifiers, it carries neither, and behaves exactly like a bare leaf. Excluding it is what Objective 3.30 already depended on (the reused-parameter-name collision); a purely mechanical rule would have silently regressed that already-fixed bug.

### 198. The actual classification fix: require at least one surviving COMPOUND member before trusting any leaf match at all
Rather than exclude leaves from the per-member check entirely (which would wrongly inflate the changed-count even for the common, legitimate case of a small edit inside an otherwise-intact function -- untouched leaves like an unrenamed parameter are genuine, reliable evidence there), the fix is narrower: compute `hasCompoundAnchor` -- does at least one COMPOUND member of this record still fully match somewhere in the current file? If yes, the existing per-member check runs completely unchanged (this is the common, already-correct case, proven by every existing rename/partial-edit test still passing unmodified). If no compound member survives at all, nothing of this record's actual content remains, and the whole record is treated as fully stale -- `changedMembers` becomes all of `record.members`, regardless of any leftover bare-leaf coincidences.

### 199. Verified by deliberately breaking it first, then against the real data that exposed the bug
Manually reverted the fix (reintroducing the naive per-member check), reran just the new regression test, and confirmed it fails exactly as expected (`Expected: "fully_stale", Received: "partially_stale"`) before restoring the fix and confirming it passes again -- proof the test is a real guard, not one that would have passed regardless. The regression test itself reproduces the exact failure shape: a documented `fib()` function fully replaced by an unrelated `buildGraph()` function that happens to reuse the bare literal `1`. Reran the real-repo diagnostic against `catalogue/third_file.ts` after rebuilding: both records now correctly resolve `status: "fully_stale"`, and the Problems tab renders them as `[error]` (with the new Delete button from Objective 3.32) instead of `[warning]`. Full suite: 112/112 (111 + 1 new). By the time of this verification, the tester had already used the new Delete feature themselves on both of `initial.ts`'s stale records in the real repo -- confirmed directly (`.rapid-docs/initial.ts.json` now shows `"records": {}`), real evidence the feature is already working for them in practice, independent of this fix.

## Objective 3.34 — Type-Level Wasn't Enough, a Real CRLF Bug, and Painting Drift Directly Onto the Code

### 200. A real, live case where "compound type" still wasn't reliable enough
Manual testing on a real repo surfaced two more mysteries in the same session: (a) a record for `buildGraph` that jumped from "40 of 72 changed" to "1 of 72 changed" purely from switching git branches and back, with no actual edits; (b) that same record's warning still quoted docText instead of a derived name, even though `buildGraph`'s own `FunctionDeclaration` clearly survived intact. Investigated both with real evidence rather than assumption.

### 201. Mystery (b): an empty array literal, and the real limit of a TYPE-level rule
Instrumented the actual anchor/bounding-box computation for the live `buildGraph` record: 46 anchors resolved, stretching the bounding box from the function's own span (201-519) all the way to 1108 -- past a completely unrelated `breadthFirstSearch`. The node responsible: an empty `ArrayExpression` (`[]`), which is typed as compound (`ArrayExpression` CAN hold elements, so it was never in `ATOMIC_LEAF_TYPES`) but, as a SPECIFIC empty instance, carries exactly as little information as a bare leaf -- every empty `[]` anywhere in the file hashes identically. `ATOMIC_LEAF_TYPES` is a type-level rule ("can this kind of node ever hold children"); what actually matters for collision-safety is instance-level ("does THIS node hold anything right now").

### 202. The fix: `isLeafNode(node, type)`, checking real field contents via `VISITOR_KEYS`, not just the type name
A node counts as a leaf if its type is in `ATOMIC_LEAF_TYPES` OR every one of its own potential child-holding fields (from `VISITOR_KEYS`) is actually empty (`null`/`undefined`/a zero-length array) for that specific instance. Applied everywhere a leaf/compound distinction already mattered: the name-derivation anchor filter and the undocumented-node overlap check (both operate on CURRENT, freshly-parsed nodes, so full instance data is available) and the `hasCompoundAnchor` classification check (which reads STORED `record.members` -- no raw node persisted, so `RecordMember` gained an optional `isLeaf?: boolean`, computed once at `writeDoc` time and falling back to the coarser type-level check for records written before this field existed). Verified: dropped the empty-`[]` anchor from 46 to 42, and the bounding box shrank from reaching 1108 down to 757 -- real, confirmed progress.

### 203. But a SECOND collision remained, and it exposed a real limit worth stating honestly rather than chasing further
Even after the `isLeafNode` fix, `drift.name` still came back `null` for the live `buildGraph` case: a `TSTypeReference` to the file's own shared `Graph` type (used in `breadthFirstSearch`'s signature) survived as an anchor, because it technically "has a child" (a `typeName` field pointing at an `Identifier`) even though, in a file built around one central shared type, a bare reference to that type carries almost as little distinguishing information as a lone identifier. Rather than keep chasing progressively narrower shapes (a number, an empty array, now a common type reference) with no natural stopping point, this was named explicitly as an open-ended problem and handed back as a real question: keep refining name-derivation specifically, or treat this as an acceptable, safe degradation (the docText-quote fallback exists precisely for cases like this, and the drift `status`/`changedMembers` count -- the part that actually matters for correctness -- was never affected by any of this).

### 204. Mystery (a) resolved instead: comments hash their own text verbatim, and git's CRLF normalization is a real, well-bounded bug
Traced independently: `buildGraph`'s `ExportNamedDeclaration` carries a `trailingComments` entry (Babel attaches the comment between two functions to both the preceding and following node) whose `value` field is the JSDoc text for the NEXT function, captured byte-for-byte -- embedded `\r\n` and all. `canonicalize()` never excluded comment/string content from hashing (only `start`/`end`/`loc`/`extra`/`tokens`/`expectedNode` were excluded), so a purely cosmetic line-ending flip (confirmed: git's Windows `core.autocrlf` behavior, triggered by the branch switch) changed that comment's exact bytes and, with it, the hash of whatever node carried it -- with zero actual code changes. Proven directly: reconstructing the current file with `\r\n` replaced by `\n` and rehashing `buildGraph`'s `ExportNamedDeclaration` produced a hash that matched the ORIGINALLY stored one exactly.

### 205. The fix: normalize line endings only at the point a string is hashed, never anywhere the real parsed positions are used
Unlike the earlier collision cases, this one has a clean, bounded fix rather than an open-ended one: `AstService.canonicalize()` now normalizes `\r\n` to `\n` for any string value immediately before it's serialized into the hash. Deliberately NOT applied to the actual parsed source text anywhere else (not in `parseSource`, not before `readFileSync`'s result is used) -- every node's real `start`/`end`/`loc` must keep matching the file exactly as Monaco and the rest of the app actually read and display it; normalizing the parsed text itself would silently shift every position after the first converted line ending and break decorations/selection. Verified directly: `checkFile` against the real, still-CRLF `buildGraph` record now reports `status: "unchanged", 0/72 changed` -- not just reduced, genuinely eliminated, since nothing about the code ever actually changed. One new `AstService` regression test (a comment hashed once with LF, once with CRLF, same fixture) deliberately confirmed to fail without the fix before being confirmed to pass with it.

### 206. A different, better-shaped idea for tying a warning to its code: paint the CURRENT code directly instead of naming it in a sentence
Given how fragile deriving a single "name" for a sentence had proven (three real collision shapes found in one session), a different framing was proposed and refined through discussion: instead of describing WHERE a warning is in prose, highlight the actual current code it's about, the same way "documented" sections already get a green decoration. Two real constraints shaped the final design: (1) there's no stored "old" text to diff against -- only hashes -- so a literal git-style line diff isn't possible; a file-content cache does exist (`LiveWatchService.contentCache`), but it's in-memory only, keyed by path rather than by doc record, and holds only the most-recently-seen content, not "the content when this record was written," so it doesn't solve this either. (2) Painting a MERGED bounding box (the same technique name-derivation uses) is unsafe for a visual feature specifically: a single coincidental outlier anchor would visually paint everything in between it and the real match, including unrelated code -- a much more visible, more confusing mistake than a name falling back to a docText quote. The chosen design instead decorates each individual anchor's own span directly, never merged: a stray outlier just adds one small, isolated, separate decoration, never swallows unrelated code between two real matches.

### 207. First implementation: a dedicated IPC channel returning every range at once, painted automatically
`DriftResult` gained `matchingRanges: {start, end}[]` -- the CURRENT position of every individual anchor already computed for name-derivation, exposed directly instead of being discarded after deriving `name`. A first version added `DocumentationService.getHighlightRanges()`, collecting `matchingRanges` from every `partially_stale` record (warning) plus every `collapseToTopLevel`-grouped undocumented node (info), wired through a new `docs:getHighlightRanges` IPC channel and folded into `refreshDocumentedSections()`/`renderDecorations()` so every problem in the file painted automatically, all the time, the moment a file opened or changed.

### 208. Verified working, then immediately corrected by real usage: automatic-everything was the wrong shape
End-to-end verification in a real Electron session confirmed the automatic version worked exactly as built (a real test-script bug was caught along the way too: git's `autocrlf` had silently converted a scratch file to CRLF, shifting a hardcoded LF-calibrated highlight offset off the function's real boundary -- fixed by disabling `autocrlf` for that scratch repo, not an app bug). But real usage immediately surfaced the actual problem: with every warning and every undocumented node tinted at once, all the time, the tester reported it was hard to quickly grasp what any one color-coded region actually meant without separately going to compare the two branches by hand -- and, more concretely, asked for real control: highlighting should not appear at all until a specific Problems row is clicked, and then only that row's own code should light up.

### 209. The redesign: position data rides on the message itself, no separate fetch needed
Rather than a dedicated "give me all the ranges" endpoint, `Message` itself gained `ranges: {start, end}[]` -- populated from `drift.matchingRanges` for a `partially_stale` warning, from the node's own `{start, end}` for an `info` message (one node, one exact range, no derivation needed at all), and left empty for `fully_stale`/error and for messages that were never about a specific position (a parse failure, a deleted-file notice). This let `getHighlightRanges()` and its IPC channel be deleted outright rather than kept alongside the new path -- the position data now travels with the exact message a user would click on, through the exact same `messages:live`/`getCatchUpMessages` channel that already existed, with no new plumbing at all.

### 210. The renderer: nothing highlighted by default, at most one problem's worth at a time
`renderDecorations()` no longer paints a warning/info layer automatically -- only the pre-existing green "documented" layer stays always-on. A new `activeHighlight` (`{key, severity, ranges} | null`) holds at most one problem's worth of ranges, set only by clicking a Problems row's label (specifically the label, not the checkbox or the delete button, following the same non-overlapping-click-target pattern already used for archive/doc-section rows). Clicking the same row again toggles it off; clicking a different row replaces whichever was showing. The clicked row also gets a visible `active-highlight` outline in the Problems list itself, so the connection between "this text" and "this code" is legible in both directions, not just editor-side. A live recheck (`renderFileStatus()`) re-derives `activeHighlight` from the CURRENT message with the same key every time, rather than trusting the stale one: if the same problem still exists, its ranges refresh (in case something nearby shifted); if it's gone (fixed, or cleared), the highlight clears itself automatically.

### 211. Verified end-to-end in the real Electron app: nothing shows until clicked, exactly one problem at a time
A fresh scratch repo, documented a function, then renamed a variable inside it to create a real partial-staleness warning alongside the file's pre-existing undocumented `const x`. Confirmed directly: zero decorations of either color before any click; every Problems row (including info rows) is clickable since each carries real ranges; clicking the warning row shows exactly its own highlight and marks that row active, with nothing else lit; clicking the same row again clears it completely; clicking an info row instead shows only that node's blue highlight. Full suite: 115/115 (116 - 3 superseded `getHighlightRanges` tests + 2 new `Message.ranges` tests).

## Objective 3.36 — The File Tree Doesn't Know `git ls-files` Lies About Deleted Files

### 212. Reported precisely, with the terminal output as proof the backend already knew
Continuing Section 4 of the manual test checklist: deleted `catalogue/third_file.ts` from OUTSIDE the app (no `git rm`, no commit) while rapid-docs was running. The terminal correctly logged `[live][warning] "catalogue/third_file.ts" no longer exists. Its documentation is being removed: ...` for both of its records -- proof the backend genuinely detected the deletion. But the file tree in the UI still showed `third_file.ts`, and clicking it did nothing, as if the file still existed.

### 213. Root cause, confirmed directly rather than assumed: `git ls-files --cached` reflects the INDEX, not the disk
`files:list` (which builds the tree) calls `GitService.listWorkingTreeFiles`, which runs `git ls-files --others --exclude-standard --cached`. `--cached` lists whatever is in git's INDEX -- a plain filesystem delete, with no `git rm` and no commit, never touches the index at all, so the file keeps coming back from this command even though it's genuinely gone from disk. `onLiveMessages` already calls `loadFileList()` on every live event (fixed back in Objective 3.19 for the opposite case -- a newly created file not appearing), so the refresh WAS happening on schedule; it was just re-fetching a list that still, incorrectly, included the deleted file.

### 214. This exact gap was already known and guarded against -- just not everywhere
Grepping for other callers of `listWorkingTreeFiles` turned up two that already defend against precisely this: `SyncService.reconcile()` (with its own comment: "git's index can still list a file here even after it's been deleted from disk without `git rm`") and `LiveWatchService.start()`'s cache-priming loop -- both independently wrap the result in `existsSync()` before using it. `files:list` was the one caller that had never been given the same treatment, because it was added later and nobody re-derived the same lesson for it.

### 215. The fix: filter at the one authoritative source, not at every call site that happens to remember
Moved the `existsSync` filter INTO `listWorkingTreeFiles` itself, so every caller gets a list that genuinely reflects the current filesystem, not just git's index -- removing the risk of a future fourth caller forgetting the same guard. The two existing defensive checks in `reconcile()` and `start()` became provably redundant once the source itself was fixed, and were removed rather than left as harmless-but-confusing dead code; both already had inline comments explaining a workaround that no longer applies once the root is fixed.

### 216. Verified by deliberately breaking it first, then end-to-end in the real Electron app
A new `GitService` test (commit a file, `rmSync` it directly without `git rm`, confirm `listWorkingTreeFiles` no longer lists it) was confirmed to fail against the pre-fix code (`Received array: ["tracked.txt"]`) before being confirmed to pass with the fix restored. Then, in a real running Electron app: documented a function in `fileA.js`, deleted `fileA.js` from outside the app (a plain `unlinkSync`, uncommitted), and confirmed directly that the file tree dropped `fileA.js` immediately (no repo switch or restart needed) while `fileB.js` stayed, and that the archive correctly gained one entry with `originalFileId: "fileA.js"` and the right docText. Full suite: 116/116 (115 + 1 new).

### 217. Immediately after this fix, the SAME class of gap surfaced one level over: the Archive tab
Reported with both halves of the proof side by side: `.rapid-docs/_archive.json` on disk genuinely had two new, well-formed entries for the just-deleted `catalogue/third_file.ts` (real UUIDs, timestamps, docText) -- yet the Archive view in the app still read "Nothing archived." The backend had done its job correctly (again); nothing on the renderer side had re-fetched the Archive list to reflect it.

### 218. Root cause: `switchView` never refetches, and `refreshArchiveList` was only ever called after the user's OWN actions
`switchView(viewName)` (the nav-rail click handler) only toggles which `.view`/`.nav-item` element is visible via CSS classes -- it has never re-fetched anything, for any view. `refreshArchiveList()` itself was only called once at bootstrap and after the user's own attach/discard actions -- never in response to a live external event. This is the identical shape as Objective 3.19 (the file tree) and Objective 3.24 (the open file's content): `LiveWatchService` and `handleDeletedFile` correctly detect and archive the change; nothing downstream in the renderer knew to go look again.

### 219. The fix and verification: one more call, in the exact place the same lesson was already learned twice
Added `refreshArchiveList()` alongside the existing `loadFileList()` call inside `onLiveMessages` -- the one place already established (Objective 3.19) as "any live event means something on disk changed, re-fetch the things that could be affected," rather than trying to detect specifically which events are deletions. Verified in a real Electron app: opened the Archive tab first (confirmed "Nothing archived," matching the reported scenario exactly), documented a function, deleted its file from outside the app while still on the code view, then switched to Archive with no other manual refresh -- confirmed the entry now appears (`"from fileA.js ... greet() logs a greeting."`, one row), with no repo switch or restart needed. Full suite: 116/116, unaffected (a renderer-only fix, no `src/` changes).

## Objective 3.38 — A Record With No Single Containing Node, and Activity Entries That All Looked Identical

### 225. Reported with both directions of proof: storage said yes, the sidebar said no
Documented the ENTIRE `initial.ts` file in one highlight (multiple sibling top-level statements: an import, several consts, an expression -- no single function or class wrapping all of it). `.rapid-docs/initial.ts.json` genuinely gained a real record (52 members, confirmed directly in the editor). But the "Documented sections" sidebar read "Nothing documented in this file yet," no green highlight appeared, and -- separately -- the Activity tab looked completely unchanged after the action, as if nothing had happened.

### 226. Root cause: `findDocumentedNodes` can only ever find a record whose span matches SOME single node's own boundary
Confirmed directly: `findDocumentedNodes` returned `[]` for the real record, while `findRecordForSelection` (the right-click menu's own check, which uses the actual selection bounds rather than guessing from node positions) correctly found it. The reason: `findDocumentedNodes` iterates over every individually-walked AST node and tries ONLY that node's own natural `[start, end]` as a candidate span. That's sufficient when a record corresponds to one syntactic construct (a function, a class, a variable) -- there's always exactly one node whose own boundary matches. A record spanning MULTIPLE sibling statements with no common containing node -- the whole file, or several consecutive statements inside a function -- has no such node at all, so no candidate could ever match it, no matter how the algorithm verifies the hash.

### 227. The general fix, chosen over a narrower one: sibling ranges, derived from structure rather than hand-picked node types
Two options were on the table: a narrow fix (one extra "whole program" candidate, covering only the exact reported case) or a general one (candidates for every contiguous run of 2+ children of ANY array-of-nodes field, anywhere in the tree -- also covering "several consecutive statements inside a function," not just the top level). The general fix was chosen. `AstService.findSiblingRanges()` walks the raw AST (parallel to `walkAllNodes`'s own recursive shape) and, for every array field whose elements are ALL genuine positioned nodes, generates every contiguous multi-element range's `{start, end}` as an additional candidate -- generic on purpose (any qualifying array counts, not a hand-typed list of "body" field names that could go stale as new node shapes are added), consistent with `ATOMIC_LEAF_TYPES` already being derived from Babel's own metadata rather than guessed by hand earlier this session. `findDocumentedNodes` now tries these sibling-range candidates alongside the existing individual-node candidates -- no change at all to the per-candidate verification logic itself (the COMPLETE combined hash still has to match exactly, the same protection that already prevented two functions with identically-named parameters from being confused with each other), just more spans offered up to check.

### 228. Verified by deliberately breaking it first, against both the general case and the real, already-broken repo data
Two new regression tests (a whole-file record with no containing node; several consecutive statements inside a function body, proving the fix isn't special-cased to the top level) were confirmed to fail without the fix (`Expected: 1, Received: 0`) before being confirmed to pass with it restored -- plus three direct `AstService.findSiblingRanges` unit tests. Reran `findDocumentedNodes` against the REAL, already-existing `initial.ts` record that exposed the bug: it now correctly resolves to one entry (`type: "Range", start: 0, end: 370`) instead of an empty array. Verified live in a real Electron app too: selected an entire file with a real `Ctrl+A`, documented it, and confirmed the sidebar now shows the record (not "Nothing documented") with the green highlight actually painted (22 decoration spans). Full suite: 121/121 (116 + 5 new).

### 229. The Activity concern turned out to be a second, smaller, genuinely real gap -- not a misreading
Checked directly rather than assumed: every `addActivityEntry` call site only ever logged a generic, file-agnostic string (`"Documented."`, `"Select some code in the file above first."`) -- `relativePath` was never part of the text at all. So documenting a second file almost certainly DID add a new entry; it just read byte-for-byte identical to the previous file's entry, making it impossible to tell whether anything had actually happened. Fixed by appending `(${currentRelativePath})` to every entry generated from the write-doc-button handler once a file is known to be open (every case except "Open a file first," which fires precisely when there isn't one). Verified live: the Activity tab now reads `"[success] Documented. (sample.js)"`, distinguishable from any other file's entry at a glance.

## Objective 3.42 — An Uncaught Parse-Failure Exception Was Silently Freezing the Problems Panel

### 234. Reported with three screenshots, precisely enough to diagnose without guessing
Manual testing on Section 7's "broken syntax" checklist item: opened a file with real `[info]` messages, then switched to a second, genuinely unparseable file. The Problems panel kept showing the FIRST file's exact info messages (matching line numbers and all) while the editor and file-tab header had already switched to the second, broken file -- until clicking one of the (wrong) rows suddenly made the correct `[error] ... failed to parse` message appear.

### 235. Root cause, found by reading the actual code rather than guessing: an uncaught exception aborts the rest of openFile()
`DocumentationService.findDocumentedNodes` throws (`"Cannot locate documented nodes: file failed to parse"`) when the file it's asked to check doesn't parse at all -- correct and intentional on the backend. But `refreshDocumentedSections()` (the renderer function that calls it) had no try/catch around that call. Since `invokeOrThrow` (the IPC layer, Objective 3.29) faithfully re-throws a backend error as a real local exception, this uncaught throw aborted `refreshDocumentedSections()` immediately -- and because `openFile()` `await`s that call BEFORE its own final `renderFileStatus()` line, the SAME exception aborted `openFile()` too, skipping the one call that would have refreshed the Problems panel. Monaco's content and the file-tab header had already updated (that happens earlier in `openFile()`), so everything LOOKED like it had switched files except the one panel that hadn't. Clicking a Problems row worked purely because that handler (`toggleHighlight`) calls `renderFileStatus()` directly, bypassing the broken chain -- by then the real error message had already arrived independently via the live-check pipeline, which was never affected by any of this.

### 236. The fix: catch the parse failure locally, fall back to "no documented sections," let everything downstream still run
`refreshDocumentedSections()` now wraps the `findDocumentedNodes` call in a try/catch, falling back to an empty list on failure -- an honest answer, since there's no reliable way to locate documented sections in code that isn't valid JS/TS at all. This lets the rest of the function, and critically `openFile()`'s own trailing `renderFileStatus()` call, run unconditionally regardless of whether the newly-opened file happens to parse. The actual "this file failed to parse" error message is untouched by this fix -- it was always generated correctly by `SyncService`'s own, separate try/catch (Objective 3.20-era) and delivered via the normal Problems/Dashboard message pipeline; this fix only concerns the sidebar/decoration lookup that was blocking everything after it.

### 237. Verified by reproducing the exact reported sequence in the real Electron app
A fresh scratch repo: opened an undocumented file first (confirmed a real `[info]` row present, as a genuine "stale content" baseline), broke a SECOND file's syntax on disk, then clicked directly into it -- mirroring the exact sequence reported. Confirmed the Problems panel showed the second file's own `[error] ... failed to parse` message IMMEDIATELY upon opening it, with no stale content from the first file and no need to click anything first. Full suite: 121/121, unaffected (a renderer-only fix, no `src/` touched).

### 238. Asked directly whether there were more of these -- a full audit found seven more
Rather than reassure without checking, every `window.rapidDocs.*` call site in `renderer.js` was grepped and traced individually against its actual backend implementation, checking specifically: can this call throw, and if it does, is the exception caught anywhere before it can abort something a user would notice? Seven more genuinely uncaught call sites turned up, all the same class of bug as Objective 3.42, just at different action points:

- **`deleteSection`** (Documented-sections Delete button, and the code area's right-click "Delete documentation") -- `deleteRecord` uncaught; on failure, `refreshDocumentedSections()` (the line right after it) never ran, so the row stayed with no explanation.

## Objective 3.43 — Pulling a Collaborator's New Documentation Never Updated Anything Live

### 241. Reported with two screenshots that turned out to be one root cause
While starting Section 8 (multi-collaborator testing): after `git pull`-ing a teammate's newly-documented function into Clone B while rapid-docs was open, the Problems tab kept showing a stale "no documentation yet" message for that exact function -- until navigating away to another file and back, which correctly showed it as documented. ### 242. Confirmed with hard evidence before proposing anything: the pulled commit touched only the storage file
`git show --stat` on the actual pulled commit showed exactly one file changed: `.rapid-docs/catalogue/maths_multiply.ts.json`, 90 insertions, nothing else -- the source `.ts` file itself was never part of that commit at all, because documenting existing, unmodified code never requires editing it. Cross-checked against `LiveWatchService`'s `SOURCE_FILE_PATTERN = /\.(js|jsx|ts|tsx)$/`, applied at the top of every one of `handleChange`/`handleAdd`/`handleUnlink` -- a `.json` file changing is invisible to it, unconditionally, by a filter that was never built with `.rapid-docs/*.json` changing ON ITS OWN in mind.

### 243. Why this specifically matters for multi-collaborator use, more than any single-user scenario
Every single-user live-watching scenario tested so far (Sections 5 and 7) always involves the SOURCE file changing too -- writing a doc through the UI, editing code, renaming, deleting. Pulling a collaborator's documentation for code you ALREADY have, byte-for-byte unchanged, is the one realistic case where ONLY the storage file moves. That's exactly Section 8's core scenario, which is why it had never surfaced before reaching that section.

### 244. The fix: treat a `.rapid-docs/<path>.json` change as a signal to recheck `<path>`, not just itself
Added `deriveSourcePathFromStoragePath()`, checked at the top of all three chokidar handlers (`handleChange`/`handleAdd`/`handleUnlink`) before the existing `SOURCE_FILE_PATTERN` check: strips the `.rapid-docs/` prefix and `.json` suffix from the relative path, and if what's left looks like a real source file, triggers the exact same `syncService.handleFileEvent()` recheck as if THAT source file itself had just changed. `_archive.json` (repo-wide, not mirroring any single source file) is excluded automatically and for free -- stripping its prefix/suffix leaves `_archive`, which `SOURCE_FILE_PATTERN` correctly rejects, no special case needed. Deliberately bypasses the existing rename-correlation machinery entirely (the `pendingAdds`/`pendingUnlinks` content-similarity pairing) -- that logic is specifically about detecting whether two SOURCE-code events are the same file renamed, a question that doesn't apply to storage-file changes at all; a direct, immediate recheck is simpler and correct.

### 245. Verified with three new tests, confirmed as real regression guards by deliberately breaking the fix first
Added directly to `live-watch.service.spec.ts`, using the same real-chokidar-against-a-real-git-repo pattern already established there: (1) call `writeDoc` directly against an UNDOCUMENTED, already-on-disk source file -- since `writeDoc` only ever writes the storage `.json`, the source file is never touched at all, exactly mirroring what `git pull` does -- and confirm the watcher emits a fresh, no-longer-`info`-severity message for that source path; (2) delete a record's storage file directly and confirm the reverse also works, correctly re-flagging the source as undocumented; (3) confirm `.rapid-docs/_archive.json` specifically still produces no message at all. Temporarily stubbed `deriveSourcePathFromStoragePath` to always return `null` and confirmed both new positive-case tests then failed with a timeout (`waitFor: condition never became true`) before restoring the real implementation and confirming all three pass again. ## Objective 3.44 — A Record Made Entirely of Leaf Content Could Never Satisfy Its Own Staleness Check

### 246. Found immediately while retesting the previous fix, via a genuinely new scenario: documenting a bare comment
While retesting Objective 3.43 live, documenting a single comment (not attached to any function -- just the comment itself, standalone) produced an immediate `[error] "..." no longer matches any code in this file` -- while the SAME record showed up correctly, unchanged, in the "Documented sections" sidebar at the exact same moment. Two independent computations flatly disagreeing about the same record, with nothing on disk having changed at all.

### 247. Root cause: Objective 3.33's own fix has a blind spot for records with no compound members to offer
Confirmed directly: the record's `members` array had exactly one entry -- the `CommentLine` node itself, correctly flagged `isLeaf: true` (a comment has no substructure, so `VISITOR_KEYS` for it is empty, and `isLeafNode` correctly says so). Objective 3.33's `hasCompoundAnchor` rule requires at least one COMPOUND member to still match before trusting anything -- a rule built specifically to stop coincidental leaf collisions from hiding a genuinely dead record. But a record made ENTIRELY of leaf content, like a bare comment, can never have a compound member to offer in the first place, by its own composition -- not because anything changed. The rule, applied unconditionally, always failed for it, regardless of whether the comment was byte-for-byte untouched.

### 248. The fix: only require a compound anchor when the record could actually have one
Added `hasCompoundMember` -- does this record contain ANY compound member at all, regardless of whether it currently matches? If not, the compound-anchor gate is skipped entirely and the record falls back to the plain per-member check Objective 3.33 was built on top of, since there's nothing better available to check against for a leaf-only record. If the record DOES have compound members, behavior is completely unchanged from Objective 3.33 -- this is a strictly additive fix, touching only the one case that previously had no path to ever pass at all.

### 249. Verified by deliberately breaking it first, then against the exact real records that exposed the bug
A new regression test (document a standalone comment, check immediately with nothing changed) was confirmed to fail exactly as reported (`Expected: "unchanged", Received: "fully_stale"`) before the fix, and pass after. Re-ran `checkFile` directly against the real repo's `catalogue/new_third_file.ts` -- the exact two comment-only records that produced the reported error messages -- and confirmed all six of that file's records (comment-only and function-level alike) now correctly report `status: "unchanged"`, with zero error messages generated. Full suite: 125/125 (124 + 1 new).

## Objective 3.45 — `findDocumentedNodes` Rebuilt Three Times Chasing the Same Question From Three Directions

### 250. The sidebar's own "what's documented" query never shared logic with `checkFile`'s staleness check, and it showed
`findDocumentedNodes` (drives the "Documented sections" sidebar and the green highlight's data) worked by enumerating candidate spans up front -- every individual AST node's own boundary -- and checking each one against stored `recordId`s. That has no way to represent a record spanning MULTIPLE sibling statements with no single node containing all of them, which is exactly what a whole-file doc, or a doc covering several consecutive statements inside a function body, actually is. First fix: `AstService.findSiblingRanges()`, generating an extra candidate for every contiguous run of 2+ array-of-node-children (generic over any such array, not hand-written per-container).

### 251. A second, unrelated gap in the same function: a comment is a property, not a sibling
Documenting a bare standalone comment, or a comment together with the function it annotates, never showed up in the sidebar either -- confirmed via `findRecordForSelection` (used by the right-click Edit/Delete menu) correctly finding the SAME record that `findDocumentedNodes` returned nothing for, proving the record itself was intact and matching. Root cause: Babel attaches a comment to the node it precedes via a `leadingComments`/`trailingComments` PROPERTY, never as a sibling array element -- so no sibling-range candidate, however generic, could ever be generated to span both. This was the third distinct "candidate shape" gap found in the same function (individual node, sibling range, comment-attached-as-property), and the user asked explicitly for a general fix rather than a fourth patch.

### 252. The rebuild: record-driven instead of candidate-driven
Rather than enumerate candidate spans and check each, the rewritten algorithm starts from each STORED record and asks where its content currently lives: for every member hash, look up its current position(s) via a `positionsByHash` map built once from a full walk of the live file; if any member's hash doesn't exist anywhere currently, the record is stale (skip -- handled elsewhere); otherwise take the bounding box (min start / max end) across the member positions and do the same exact verification as before -- `filterByHighlight` over that box, rehash everything found, compare to the stored `recordId`. This needs no candidate enumeration at all, so `findSiblingRanges()` became genuinely dead code (confirmed via grep -- its only caller was the code just replaced) and was removed entirely, along with its 3 tests.

### 253. The rebuild's own regression: a reused leaf can stretch the box across unrelated code
Two previously-passing tests broke immediately: an `add(a, b)` / `sub(a, b)` pair sharing generic parameter names, and the multi-statement-inside-a-function-body case. Cause: taking the bounding box across EVERY member indiscriminately lets a coincidentally-shared leaf hash (identifier `a`, say, appearing in both functions) pull the box out to cover code that was never part of the record at all. Fixed the same way as Objectives 3.31/3.33/3.44 fix similar leaf-collision risk elsewhere: prefer COMPOUND members for the bounding box, falling back to every member only when the record has zero compound members (a comment-only record, per Objective 3.44).

### 254. That same fix broke the ORIGINAL bug it was meant to solve: comment-plus-code
Preferring compound members unconditionally excludes a record's own leaf-type leading/trailing comment from the bounding box whenever the record ALSO has compound members -- which a comment-annotating-a-function record always does. A node's own `start`/`end` never include an attached comment's text (the comment is a separate range immediately before it); excluding the comment left the box starting at the function itself, never reaching back to the comment -- so the final verification hash came out missing the comment member and never matched. New regression test (`writeDoc` a JSDoc block together with the function it documents, then call `findDocumentedNodes`) reproduced this exactly: `expect(found.length).toBe(1)` received `0`.

### 255. An intermediate fix: re-admit a leaf only when it's structurally attached to one of the record's own compound members
Rather than guess by distance ("is this leaf's position near the box"), this fix read the relationship directly off Babel's own comment-attachment data: for each of the record's compound members' CURRENT node objects, collect every position appearing in its own `leadingComments`/`trailingComments`/`innerComments` (the only three properties that ever hold comment nodes -- so this could never accidentally re-admit a non-comment leaf like a shared identifier). A leaf member was added back into the bounding box only if one of its current positions matched one of those collected comment positions exactly. This passed the new synthetic test and the full suite (123/123) -- but "passed my own test fixture" turned out not to be the same claim as "works on real code," per Objective 3.46 below.

### 256. Real data broke it within minutes of retesting: compound members duplicate too, not just leaves
Back in the real app, re-verifying against the actual repo surfaced that almost nothing in `catalogue/new_third_file.ts` showed up in the sidebar anymore -- not just the comment-plus-code case, but plain records like "documenting the for loop" and "documenting first function" that had worked before any of today's changes. Root cause, confirmed directly against the real file: `encoded += \`${count}${currentChar}\`;` appears twice in `runLengthEncode` -- once inside the for-loop (part of the "for loop" record) and again, identically, as the trailing flush statement right after the loop (not part of it). Both are the same hash. The "prefer compound members" rule from Objective 3.45 §253 took *every* current position of a compound member indiscriminately, same as the leaf version of this bug -- so the second, unrelated occurrence pulled the box out past the loop's real end, and the exact verification failed for a reason that had nothing to do with comments at all. This is why Objective 3.46 exists as a separate entry rather than a footnote: it's a materially deeper version of the same class of bug, found only because real code has repeated idioms that a hand-written fixture doesn't happen to include.

## Objective 3.46 — One Unified Rule Instead of Three Special Cases, Verified Against Every Record in the Real Repo

### 257. The insight: "prefer compound" and "re-admit attached comments" were both patches for the same missing idea
Every version up to this point tried to classify members (leaf vs. compound, attached-comment vs. not) and special-case each classification. The real fix needed is simpler and doesn't care about node type at all: a member is a trustworthy anchor exactly when the file *currently* has as many occurrences of its hash as the record needs -- zero guessing required, true whether it's a `ForStatement` or an `Identifier`. Everything else is genuinely ambiguous and has to be resolved relative to whatever's already trustworthy.

### 258. The algorithm: claim the unambiguous, then grow outward by nearest distance
For each distinct hash a record needs, if the file's current occurrence count for that hash exactly equals how many times the record needs it, claim all of them immediately (unambiguous by elimination -- no distance check needed). Once at least one member is claimed, repeatedly find whichever *still-needed* occurrence, across every remaining ambiguous hash, sits closest to the box established by everything claimed so far (0 if it's already inside the box), claim it, and recompute the box -- one occurrence at a time, so a hash needed twice (a param type and a return type, both bare `: string`) can correctly claim two *different* occurrences instead of the same nearest one twice. A record with no unambiguous member at all (everything it needs also exists elsewhere in matching quantity) has nothing to grow from; every occurrence of every member is used, same safety-netted fallback as always. This subsumes both Objective 3.45 fixes -- "prefer compound" and "re-admit attached comments" -- as special cases of one rule, and the leaf/compound distinction (`isLeaf`/`ATOMIC_LEAF_TYPES`) is no longer read by this function at all.

### 259. Verified against all 12 records already sitting in the user's real, in-use repo -- not just fixtures
Ran the rebuilt `findDocumentedNodes` directly against every `.rapid-docs/*.json` storage file across the whole real test repo: 8/8 in `catalogue/new_third_file.ts` (including the comment-plus-code case, the for-loop case, and two records whose own composition turned out to be an unusual partial-signature-only selection from earlier testing), 1/1 in `catalogue/maths_multiply.ts`, 2/2 in `first_file_v3.ts`, 1/1 in `second_file.ts` -- 12/12 total, all pre-existing records the user had created across many earlier test sessions, not new fixtures written to order. Full suite still 123/123, `npm run build:all` clean.

### 260. A side effect worth recording: two docs the user deleted, believing them broken, were still sitting in git
While investigating the real-repo failures, the user had already deleted two records (`"documenting inner of third function"`, `"documenting the chunks variable."`) assuming they were casualties of the bug. `git status` on the storage file showed it as modified but never committed -- so the pre-deletion version was still retrievable via `git show HEAD:<path>`. Recovered both by merging their entries back into the current storage file (preserving the four records added since), verified each one against the current source first (`checkFile` reported `unchanged` for both, `findDocumentedNodes` found both) before writing anything, rather than assuming the old data was still valid. Ended at 10/10 records resolved for that file. Worth remembering as its own small lesson: this storage format's plain-JSON-in-git design means a deletion made through a buggy UI is not actually destructive as long as nothing's been committed since -- the git history is a real undo button here, not just a backup.

### 261. Confirmed end to end: TEST-CHECKLIST.md Section 8.1 (multi-collaborator) now passes cleanly

## Objective 3.47 — There Was No Way to Resolve a Drift Warning at All

### 262. Found while preparing to walk through Section 8.3 ("A resolves it, B sees resolution"), before any code was written
Tracing the actual UI paths for "fix the doc (Edit)" against a partially-stale record turned up nothing: the Problems tab's delete button is deliberately restricted to `severity: "error"` (fully stale) -- the existing code comment says so explicitly, on the reasoning that a warning is "still real, accurate content worth keeping and updating, not deleting." But nothing implements the "updating" half. Right-click "Edit documentation" only exists via `findRecordForSelection`'s EXACT hash match, which a drifted record can, by definition, never produce again from any current selection. Clicking the warning row itself only highlights and scrolls to it. `writeDoc` has no notion of an old, overlapping record to retire -- documenting the current code fresh would just add a second record, leaving the original warning to sit there permanently, with no path to remove it. This would have made Section 8.3, as written, a dead end -- not a testing mistake, a genuine missing capability.

### 263. The design: exact-match and drift-resolution are structurally disjoint, so the fix is purely additive
Key fact: an exact hash match can only ever exist for genuinely unchanged code -- once a record drifts at all, no future selection recomputes its old hash again. So `findRecordForSelection` returning a match and a record being stale are mutually exclusive by construction, meaning the existing, already-tested "Edit documentation"/"Delete documentation" path (exact match found) needed zero changes. The new logic only had to grow the OTHER branch -- the one that, today, unconditionally offers "Document selection" regardless of whether the selection overlaps something stale.

New backend method `findStaleRecordForSelection` reuses `checkFile`'s own already-tested drift computation rather than inventing new logic: filters to `status === "partially_stale"` (deliberately excluding fully-stale -- with zero surviving compound anchors there's no position left to associate a selection with, and the existing error-severity Delete button already covers that case), and checks whether the selection overlaps the record's `matchingRanges` (the same current-anchor-position data that already draws the warning highlight). `updateDriftedDoc` retires the old record and writes the new one against the same loaded storage object in one save -- atomic from the caller's perspective, no window where a failure partway through could leave both gone or both present -- and reuses `writeDoc`'s own duplicate-record guard for the case where the new selection happens to already match some other existing record.

### 264. UI: a visibly distinct menu item and a mode-switching submit button, not a silent repurposing
Right-click, when no exact match exists, now also checks `findStaleRecordForSelection` and offers "Update documentation (code changed)" -- deliberately not reusing the "Edit documentation" label, so there's no ambiguity between "editing text on unchanged code" (today's tested path) and "replacing a drifted record" (this new one) either while testing or reading the code later. Chosen over a second, separate input panel (which the archive-attach flow uses for its own pending-selection pattern) since this action shares the exact same "select code, type text, submit" shape as ordinary documenting -- reusing the existing doc-bar input just needed a `pendingDriftUpdate` flag (mirroring `pendingArchiveId`'s existing precedent) to redirect the NEXT submission to `updateDriftedDoc` instead of `writeDoc`, consumed once and cleared regardless of outcome so a later, unrelated submission can never be silently misdirected. Pre-fills the old docText (matching `editSectionInline`'s existing behavior for ordinary edits) and relabels the submit button to "Update Documentation" while pending, so the mode is visibly, not just functionally, different.

### 265. Verified against real, currently-drifted data, then reverted before handing back
8 new backend tests (unambiguous overlap match, no-overlap null, nothing-drifted null, fully-stale null, successful replace-and-resolve, nonexistent-record throw, duplicate-record throw, parse-failure throw) -- full suite 131/131, both `tsc --noEmit` projects clean, `npm run build:all` clean. Beyond the fixtures: ran the full flow directly against the user's own real, currently-partially-stale `catalogue/maths_multiply.ts` record from the Section 8.2 test still sitting in Clone A -- `findStaleRecordForSelection` found it, `updateDriftedDoc` replaced it, and a fresh `checkFile` afterward correctly reported the new record `unchanged`. Backed up the storage file first and restored it immediately after confirming the result, rather than leaving a placeholder docText sitting in the user's real test data -- Section 8.3 itself was left for the user to run live, through the actual UI, since that's the point of the test.

## Objective 3.49 — A Recent-Repos List, Built and Verified as Pure Logic Before Touching the App at All

### 268. The user designed the core rotation algorithm on paper, in Python-flavored pseudocode, and asked for it to be tested before implementation
Modeled on VSCode/Antigravity's own "Workspaces" picker: a fixed-capacity (15), most-recently-used list of repo paths. The user's own two-function design (a circular buffer with a rotating write-pointer, `persistenceIndex` always pointing at the oldest slot) was implemented as `recordRecentRepo`/`listRecentRepos` in a new, framework-independent module (`src/workspace/recent-repos.ts`) -- deliberately plain functions, no class, every piece of state passed explicitly, so it could be fully verified in isolation before any wiring existed.

### 269. A real gap found in translating the user's OWN pseudocode, not a flaw in the algorithm itself
The user wrote the read-back logic relying on Python's negative-array-index wraparound (`arr[-1]` is the last element) -- correct in Python, but JavaScript's negative indices don't wrap at all (`arr[-1]` is `undefined`). Confirmed for real: ran the not-yet-full-buffer case in actual Python first and watched it throw `IndexError` past the fill point (Python only wraps ONE cycle, contrary to an initial assumption it would repeat), which shaped the real fix -- bound the read loop by `len(repoArray)`, not `maxRepos` (the two are only ever equal once genuinely full), and made the wraparound explicit for TypeScript (`((idx % len) + len) % len`) rather than relying on a language feature TS doesn't have. Verified by deliberately reverting to the bare `%` (the naive, Python-only-safe version) and confirming it produced `undefined` entries in 4 of 6 tests, then restoring the fix.

### 270. De-duplication was a separate, additive feature layered on top of the (already correct) base algorithm, not a fix to it
The base algorithm has no notion of "already in the list" -- reopening the same repo twice would rotate in a second, duplicate entry, wasting slots. Adding de-dup (`recordRecentRepoDeduped`) surfaced its own real bug on the first attempt: a naive "splice the duplicate out, then call `recordRecentRepo` normally" was tried, passed all 10 tests written against it, and was still wrong -- every one of those tests happened to leave `persistenceIndex` at `0` throughout, and splicing a duplicate out of a genuinely full array (`persistenceIndex` non-zero, from a real prior rotation) drops it below capacity, so `recordRecentRepo`'s append branch fires and returns `persistenceIndex` UNCHANGED -- for that specific array/index pair this silently reconstructed the IDENTICAL state, so reopening the repo produced no visible change and never promoted it to the front. Fixed by reading the correct final order out with the already-proven `listRecentRepos`, moving the repo to the front, capping at `maxRepos`, and replaying the result oldest-to-newest through the already-proven `recordRecentRepo` against a fresh buffer -- composition of two already-tested primitives, no new mutation logic to separately reason about. Confirmed the fix is load-bearing the same way: reverted to the naive splice, watched a newly-added test (specifically constructed with a non-zero `persistenceIndex` before the reopen) fail, restored the fix.

### 271. Wired into WorkspaceService and the empty-state UI, verified end to end including a real cross-restart
`recordOpenedRepo`/`listOpenedRepos` extend the same `Preferences`/`preferences.json` `WorkspaceService` already owned for `lastRepoPath` -- `recentRepos`/`recentReposIndex` persisted together, every time, since the whole point of `persistenceIndex` is lost if it doesn't survive a restart alongside the array. A new test constructs a SECOND, fresh `WorkspaceService` instance with no in-memory state at all to prove this -- a real simulation of the cross-restart case, not just an in-memory round-trip. `main.ts` gained `workspace:openPath` (opens a specific path directly -- no OS dialog -- for clicking a Workspaces row) alongside the existing dialog-driven `workspace:switch`, both sharing one `openRepoAndRecord` sequence. A live Playwright verification was attempted (an isolated `--user-data-dir`, so it couldn't touch the user's real session) but blocked by an unrelated, pre-existing environment issue -- `npx electron` on this machine launching main.js under a plain Node v24 interpreter instead of Electron's own bundled runtime (`Menu` came back `undefined`, which only happens outside a real Electron process) -- so this shipped on backend-test evidence plus careful tracing, and the user verified it live themselves afterward, confirming it worked, including a follow-up "Show More" collapse/expand (initial 4 visible, per-visit reset, not sticky) added once the user wanted to test past that count.

## Objective 3.50 — Every `.jsx` File In a Real Repo Failed to Parse, Unconditionally

### 272. Root cause: the jsx Babel plugin was never enabled at all
Found via the user opening a real React/Vite repo (`sparr-ai`) and hitting `[error] Could not check "...": Cannot check file: failed to parse` for every single `.jsx` file in it. `AstService.parseSource` only ever passed `plugins: ["typescript"]` to Babel's parser -- JSX syntax (`<Component />`) requires the separate `jsx` plugin, never enabled.

### 273. The fix is extension-gated, not unconditional -- matching why real TypeScript tooling treats .ts and .tsx differently

### 295. Profiled all 90 real files individually rather than guessing which ones were slow
Six vendored third-party library files -- jQuery, Select2, XRegExp, checked into a Django `staticfiles/` directory (git-tracked, not gitignorable the way `venv/` was) -- accounted for essentially all of it: 16.1s, 15.3s, 7.2s, 7.0s, 1.6s, 1.4s, against a combined ~50ms for the other 84 files. A full Babel AST parse of something the size of jQuery is genuinely expensive, and nobody's ever going to write per-node documentation for a vendored library's own internals.

### 296. The design question, worked through explicitly before writing anything: how to defer this cost without ever losing the benefit for a file that's actually documented
The user's own concern, stated directly: skipping large files can't come at the cost of silently losing drift-protection for a large file someone actually cares about. The resolution -- also worked out collaboratively, not unilaterally -- rests on one fact: checking "does this file have existing documentation" is cheap (a lookup on its own small `.rapid-docs/*.json` storage file), completely independent of how expensive the file's own content would be to parse. So the skip condition became `isLarge AND hasZeroExistingRecords`, not `isLarge` alone -- a file with even one documented record is NEVER skipped, checked in full on every bulk pass exactly as today, regardless of size. The skip is also reversible, not permanent: the same test is re-asked fresh every time (nothing cached), so the moment a large file gains its first documented record, every future bulk pass checks it again automatically.

### 297. What the skip actually defers, made precise before implementing: "will I still get the benefit" answered by tracing every call site of checkFile
Confirmed directly (not assumed) that simply opening/viewing a file does NOT re-run `checkFile` at all -- traced every call site: only the bulk scan, `LiveWatchService`'s live-edit handlers (an actual on-disk change), and right-click "Update documentation" ever call it. This shaped the actual fix: a new `SyncService.checkFileOnDemand(repoPath, relativePath)` re-asks the exact same skip test at the moment a file is opened -- if it's STILL true (still large, still zero docs), the bulk pass definitely skipped it, so it's checked right then; if false, the bulk pass already covered it (or it was never skippable), a genuine no-op, signaled by returning `null` rather than an empty array so the caller knows not to bother pushing a live update for nothing. Wired into `openFile()` in the renderer via a new `docs:ensureFileChecked` IPC call, right after the file loads -- invisible for every normal file, real (if occasionally slow, for something jQuery-sized) work only for the rare file this was ever about.

### 298. Every call site of checkAndReport traced and classified, not just the two obvious ones -- `fullScan()` almost got missed
Bulk, blanket callers that need the skip: `reconcile()`'s full sweep, `sync()`'s diff loop (added/modified), and `fullScan()` (the very-first-sync-for-a-repo path) -- this last one wasn't mentioned in the first pass of this discussion and would have been a real, silent gap if it had shipped without it, since it's structurally identical in shape to `reconcile()` (exhaustive, every tracked file). Targeted, single-file callers that must NEVER skip regardless of size: `handleFileEvent` (a live edit, called only by `LiveWatchService`) and `handleRenameEvent` when called BY `LiveWatchService` for a live rename -- both are real, deliberate, one-file-at-a-time signals, not blanket sweeps. `handleRenameEvent` is shared between the bulk (`sync()`'s own rename loop) and live paths, so it gained an explicit `{ allowSkipLargeUndocumented }` option rather than guessing from context -- `sync()` opts in, `LiveWatchService`'s two call sites don't, unchanged.

### 299. The size threshold alone was insufficient -- caught by testing the fix against the real repo again after implementing it, not assumed sufficient from the first profiling pass
`LARGE_FILE_THRESHOLD_BYTES = 100_000` (from real evidence: vendor files were 170KB-292KB, the largest hand-written file was ~19KB) correctly skipped 4 of the 6 slow files. But `jquery.min.js` (89,795 bytes) and `select2.full.min.js` (79,212 bytes) both sat comfortably under the threshold, byte size alone, DESPITE each still taking 7-15 seconds to parse -- minification packs the same real code into far fewer bytes than hand-written source. Line density is what actually distinguishes them: measured directly, those two files sat at ~30,000-40,000 bytes per line (essentially the whole file on 1-2 lines), while every normal file checked -- including the large, UNMINIFIED jquery.js itself -- measured under 50 bytes per line. `MINIFIED_DENSITY_BYTES_PER_LINE = 1,000` leaves a 30x-40x margin under real minified files while sitting enormously above anything a human would ever write on one line; `MINIFIED_MIN_SIZE_BYTES = 10,000` guards the density check itself from ever firing on a trivially short, genuinely-one-line file that's cheap regardless of density.

### 300. Verified with real, deliberately-broken-then-fixed regression tests for every one of the above, then against the real repo one more time
13 new tests: `reconcile()`/`sync()`'s diff loop/`fullScan()` each skip a large undocumented file and do NOT skip a large documented one; `handleRenameEvent` skips only with the option, never without; `handleFileEvent` never skips; a skip is reversible once documented; `checkFileOnDemand` returns `null` for a no-op case and real messages for a genuinely-deferred one; the density check catches an under-threshold-but-minified file, doesn't skip the same file once documented, and doesn't false-positive on a short one-liner. ## Objective 3.58 — Real Tabs: Multiple Files Open at Once, VS Code-Style Close Menu

### 310. Until now, "opening a file" meant exactly one file could ever be open -- a new request, not a bug
Every prior objective's file-viewing behavior assumed a single `currentRelativePath`; clicking a second file in the tree simply replaced the first with no way back short of clicking it again in the tree. The user asked directly for text-editor-style tabs: several files open at once, a close (x) per tab, a right-click menu matching VS Code's own (Close / Close Others / Close to the Right / Close All -- explicitly minus "Close Saved," confirmed inapplicable since rapid-docs never edits or saves files, only reads them), a horizontally-scrolling strip with no hard cap on tab count, and the Problems/Documented-sections panel continuing to react to whichever tab is currently active.

### 311. Design: one array (`openTabs`) added alongside the existing single source of truth, not a replacement for it
`currentRelativePath` already was, and remains, the one thing every other panel (Problems, Documented sections, the file tree's own `.active` highlight) reads to know "what's open right now" -- nothing about that had to change for the panel-reacts-to-the-active-tab requirement, since it already worked that way for a single file. `openTabs` (a plain array of relative paths, in the order they were opened, never reordered on activation -- matching VS Code's own default tab behavior) is purely the answer to "what ELSE is open." `openFile(relativePath)` now does one extra check before anything else: if `relativePath` isn't already in `openTabs`, push it; either way, proceed exactly as before (fetch content, fresh Monaco model, refresh panels). Clicking an already-open file -- from the tree or from its own tab -- switches to it rather than duplicating it, for free, since the push is conditional.

### 312. Close semantics worked through explicitly: only the ACTIVE tab's closure ever needs a fallback
`closeTab(relativePath)` removes the entry from `openTabs`; if the closed tab wasn't the active one, nothing else changes (the array shrinks, the strip re-renders, and that's the whole story for a background tab). Only when the active tab itself is closed does anything else happen: activate whichever tab was immediately to its left (or the new leftmost tab, if it was already leftmost), matching VS Code's own default; if it was the last tab open at all, fall back to `resetOpenFileState()` (the pre-existing "no file selected" state, unchanged). `closeOthers`/`closeToTheRight`/`closeAll` are built the same way -- filter `openTabs`, then only call back into `openFile` if the active tab happened to be among what got removed, otherwise just re-render.

### 313. `closeTab` reused for a case that has nothing to do with the close button: openFile's own two failure paths
If reactivating an already-open tab discovers its file was deleted or renamed in the exact moment of the click (the same real, live-watching race Objective 3.42 first identified for the single-tab case) -- or, separately, that the file no longer parses -- the tab now can't just sit there in the strip pointing at nothing. Both of `openFile`'s existing failure branches gained one line: if the path being opened is already a tab, call `closeTab` on it, which picks the same sensible fallback (or resets entirely) as a deliberate close would. A single close implementation, not two.

### 314. Right-click menu built on the exact same `showContextMenu` infrastructure the editor's own right-click menu and the top-bar menu already use (Objectives 3.4x, 3.53) -- no new menu system
Items that wouldn't do anything are left out of the list entirely rather than shown disabled ("Close Others" doesn't appear at all with only one tab open; "Close to the Right" doesn't appear on the rightmost tab), since `showContextMenu` has no concept of a disabled item and inventing one for this alone wasn't worth it. "Close Saved" was left out by design, not merged into "Close" -- there is no unsaved-changes state anywhere in rapid-docs to distinguish it from "Close" in the first place.

### 315. Two small pieces of reuse rather than new code: the tab's own close icon, and its label
The close (x) button reuses `ICONS.discard`, the exact same icon already used for `panel-close-button` and the archive discard button -- one visual language for "dismiss this," not a bespoke tab icon. The tab's label reuses a renamed helper: `workspaceNameFromPath` (built earlier, only for the Workspaces list's repo-folder names) became `lastPathSegment`, since "last segment of a path, either separator" is exactly what a tab's filename-only label needed too, with its one existing call site updated to match.

`node --check` on `renderer.js`, `tsc --noEmit` clean on both projects, full suite 175/175, `npm run build:all` clean, and the built `electron/dist/` output confirmed to actually contain the new tab-strip markup/code (not just the source tree).
