# VSCode Extension Parity Checklist

**Method (agreed 2026-08-10, mandatory going forward):** go section by section, in real dependency order, bottom-up. A section is only marked CLOSED once every real capability in it is verified with real evidence (a proof file, a screenshot, an exact value checked against ground truth), never just "looks right" or "compiles." This includes things that don't show up as a UI click, like resource cleanup, not just visible features. Do not start the next section until the current one is CLOSED. `electron/` and `src/` are never edited for extension-specific reasons, only for genuine, general bug fixes (like the `decorators-legacy` parser fix below); they stay as the untouched reference to check every section against.

**Section order, and why:** (1) Extension lifecycle, since every later test depends on it running cleanly. (2) `AstService`, the deepest leaf dependency. (3) `GitService`, the other leaf, independent of `AstService`. (4) `DocumentationService`, built on `AstService`. (5) `SyncService`, built on `GitService` + `DocumentationService`. (6) `LiveWatchService`, built on `GitService` + `SyncService`. (7) UI layer, built only once 1-6 are fully proven, since Archive/the right-click menu/the compose Webview all depend on `DocumentationService` methods that weren't tested yet when those UI pieces were first touched. (8) A final explicit confirmation pass on everything deliberately not ported.

### Architecture audit and rebuild (2026-08-11)

After 7.4's first version shipped, real, repeated bugs surfaced (a right-click menu showing the wrong action for the current selection; diagnostic clicks silently failing) that no amount of incremental patching fixed. At the user's explicit direction ("audit how electron worked... replicate exactly, not patch and patch and patch"), every Section 7 piece was re-compared against the actual Electron mechanism it's supposed to replicate, not just its visual result. Findings:

- **7.2 Documented Sections — confirmed already correct, no rebuild.** Electron's row click (`renderer.js:789`) is bound directly to the `section` object already in memory via closure, no re-derivation. `documentedSectionsViewProvider.ts`'s rows do the exact same thing (`item.recordId` captured directly in the click handler, looked up from in-memory `this.items`). Structurally identical to Electron.
- **7.3 Compose's `activeEditorTracker` — confirmed a necessary platform adaptation, not a deviation.** Electron's compose button read Monaco's selection synchronously at click time, reliable because Monaco lived in the same process as the button. Our Compose panel is a genuinely separate VSCode `WebviewPanel`; `activeTextEditor` goes stale the instant it has focus. There is no synchronous equivalent to reach for here the way there was in Electron -- this is a real platform difference, not a shortcut.
- **7.4 context menu — confirmed broken by design, not just buggy.** It never replicated Electron's real mechanism (compute everything fresh, synchronously, BEFORE the menu is ever shown -- `renderer.js:334-395`). It used VSCode's declarative, pre-computed `when`-gated native menu instead, which requires keeping a context key updated reactively, ahead of time -- structurally race-prone against a fast select-then-right-click, and narrowing the update timing was never going to fully close it (VSCode's own `setContext` dispatch has latency outside our control).
- **7.1 Diagnostics click-to-highlight — confirmed broken by the same root cause.** Electron's Problems row click (`renderer.js:1064`) is ALSO bound directly to the message object via closure (`onRowClick(item, key)`), no lookup. VSCode's native Problems panel gives extensions no such hook -- clicking a row just navigates the editor, forcing `diagnosticClickHighlight.ts` to reverse-engineer which diagnostic was clicked by matching the resulting selection back against `vscode.languages.getDiagnostics()`. That indirection was the actual cause of the warning/info click flakiness, not fixable with better matching logic.

**Rebuild, both closing the same class of gap:**
- **7.4** rebuilt as one static `editor/context` menu entry (`rapidDocs.showEditorActions`, no context key, no `when` beyond `editorTextFocus`) that opens a `vscode.window.showQuickPick` built from `findRecordForSelection`/`findStaleRecordForSelection` computed fresh, synchronously, at the moment of invocation -- the direct VSCode equivalent of Electron's `showContextMenu`. `selectionContextKey.ts` (the old reactive approach) deleted.
- **7.1** rebuilt: `webviews/problems/problemsViewProvider.ts`, a real `WebviewView` whose rows carry the actual `RapidDocsMessage` object directly (matching Electron's closure-bound `onRowClick` exactly) -- clicking a row posts that same object back, never reconstructed from a VSCode navigation event. Includes the checkbox/Clear Selected/Clear All/per-row Delete (error severity only) interactivity native Diagnostics can't provide at all, closing 7.6's original gap too. The native `DiagnosticCollection` is kept, unchanged, purely for squiggly underlines and the native Problems tab's own click-to-navigate -- both still real, free, valuable VSCode integration. `diagnosticClickHighlight.ts` (the reconstruction-based approach) deleted.
- Compiled clean, activation smoke-tested (proof file, timestamp fresh). **Full interactive re-verification (clicking through the actual QuickPick and Problems webview) is still needed** -- this rebuild happened while the user was away and could only be confirmed statically; do not mark 7.1/7.4 CLOSED until that happens.

- **`writeDoc`'s info message never clearing, root cause found**: `.rapid-docs/` was listed in THIS repo's own `.gitignore` (added for the tool's own dev-repo hygiene, not a general recommendation). `LiveWatchService.isIgnored()` (`live-watch.service.ts:91-96`) excludes every gitignored path from the chokidar watch entirely, so `.rapid-docs` was never watched at all -- meaning `deriveSourcePathFromStoragePath` (the mechanism that catches a storage-only mutation like `writeDoc` and rechecks the corresponding source file) could never fire. Opening Compose (a `WebviewPanel`) steals editor focus, `activeTextEditor` goes `undefined` (the same root cause documented above for 7.2/7.3), so the Problems webview wrongly cleared to empty -- even though nothing about the underlying messages had changed. Confirmed live: selected code, picked "Document Selection" (which only opens Compose, never writes anything), the info row vanished immediately; clicking back into the source file tab brought it back. Native `DiagnosticCollection` (unchanged) plus `diagnosticPositionHighlight.ts` (cursor-position based, already native-first, needed no changes) are now the ONLY Problems mechanism. Confirmed live. This is native, user-toggleable VSCode behavior (the user can turn the filter off themselves), not something in our code and not something to build a workaround for.

### Documented Sections missing a live-refresh trigger, root cause found and fixed (2026-08-12)

A live edit to the CURRENTLY OPEN file (e.g. renaming an already-documented function, causing drift) never refreshed Documented Sections -- confirmed live: the panel kept showing pre-rename data until the user switched files away and back. Audited against `electron/renderer.js` per the user's explicit request to keep checking for anything still missing, and found a real, distinct mechanism never ported: `renderer.js:1248-1259`'s `onFilesChanged` listener, separate from `onLiveMessages` (which only ever drove Problems/Dashboard/Archive/the file tree there) -- it specifically re-opens the current file when it's among the changed paths, which cascades into `refreshDocumentedSections()`. `documentedSectionsProvider.refresh()` had no equivalent trigger at all: it only ever ran on panel-visibility, active-editor-switch, and our own mutations, never in response to a live external/background change to the file already open.

Fixed by threading an `onFilesChanged` callback through `activateDiagnosticsLiveWiring` (`diagnosticsController.ts`), called from the existing `liveWatchService.on("messages", ...)` listener with the same `relativePaths` it already had -- `extension.ts` refreshes Documented Sections when the currently active file (via `activeEditorTracker`) is among them, the direct equivalent of Electron's `onFilesChanged` → `openFile` → `refreshDocumentedSections` chain.

### Real `src/` bug found via manual testing, not a porting issue: drift-anchor matching confuses structurally-identical functions (2026-08-12)

While verifying the live-refresh fix above, live-testing surfaced a genuinely different, deeper bug: two documented functions differing only by name (e.g. `division_between_two_number`/`divisor_between_two_number`, identical params and body) -- after renaming one, its "partially out of date" warning pointed at the WRONG function's code. Root cause, confirmed by reading `documentation.service.ts` directly, not guessed: `checkFile`'s per-record anchor computation (the code that decides where a drifted record's `matchingRanges` currently live) filtered the WHOLE file by hash membership alone, with each record resolved fully independently -- when a sibling function's surviving members (params, body) hash-collide with the renamed record's own surviving members, because the code is genuinely identical, there was no way to tell them apart. `findDocumentedNodes` already has smarter disambiguation for this exact "a hash has more than one current position" problem (`chooseBoundingBoxPositions`), but it was never applied to `checkFile`'s own anchor logic, and its own safety net (silently dropping an ambiguous record rather than risk showing a wrong location) doesn't transfer to a Problems warning, which still needs to report the drift, correctly located.

This is a real, pre-existing bug in shared `src/` code (equally present in Electron), not anything specific to the VSCode port -- found only because manual UI testing happened to hit the exact structurally-identical-twin-functions shape.

Fixed per the user's explicit test-first methodology: a new, minimal, controlled repro (`documentation.service.spec.ts`, "does not misattribute a drifted record's matchingRanges to a different, structurally-identical function elsewhere in the file") was written and confirmed FAILING against the original code first (`range.start` landed inside the sibling's span, not the renamed record's own) before any fix was attempted. `checkFile` was restructured: anchor resolution is now a separate pass, ordered from the most-intact record to the least (fewest changed members first) and sharing ONE depleting position pool across every record in the file, instead of each record independently filtering the whole file. Resolving the more-intact record first (whose own still-unique name gives `chooseBoundingBoxPositions` a real, unambiguous seed to grow from) and removing its claimed positions from the shared pool means a more-ambiguous, renamed sibling is only left with its own real occurrence by the time its turn comes.

**A real, harder variant found via live re-testing right after this fix, not covered by it**: renaming BOTH twins at once (not just one) still misattributed a location -- confirmed live, then reproduced with a second controlled test ("reports no matchingRanges (rather than a wrong guess) when BOTH twins are renamed and neither has a unique anchor left"), confirmed FAILING first. Root cause: the fix above depends on at least ONE of the pair still having a unique name to seed the shared pool from; when both are renamed, neither does -- their surviving params/body are still hash-identical to EACH OTHER, so there is no reliable signal left for either record, and whichever got processed first fell back to grabbing every matching position across both functions (the same original bug, just relocated), which then starved the second record of even its own real position. There is no correct GUESS to make here, unlike the single-rename case -- the honest fix, matching `findDocumentedNodes`'s own established "never wrong, sometimes missing" philosophy: before calling `chooseBoundingBoxPositions` at all, check whether the record has at least one member whose current occurrence count in the shared pool exactly matches what's needed (a real, unambiguous seed); if none exists, leave `matchingRanges` empty and `name` null rather than trust a guessed, possibly-wrong box. Full Jest suite re-run again after this second fix: 179/179 passing (178 + this new one), zero regressions.

Both fixes confirmed via Jest, then `dist/` rebuilt (`npm run build`) so the Extension Development Host actually loads the fixed backend code -- the extension imports compiled output from the root project's `dist/`, not `src/` directly, so a Jest-only pass doesn't reach the running extension on its own.

**Follow-up idea discussed at length, then explicitly DECLINED, not just deferred (2026-08-12)**: a `git diff`-based fallback (HEAD vs. working tree, or the same `lastSyncedCommit`-vs-HEAD diff `sync()` already computes) was designed in detail -- translate an ambiguous record's old, unambiguously-resolvable position (from the last commit) forward through the real diff to disambiguate its current position. Real value for the common case (a simple rename, with or without unrelated edits elsewhere), genuinely more robust than a stored position hint (which a large insertion between twins could corrupt via raw distance). But walked through its own remaining risk honestly before deciding: reorder-and-rename-together on genuinely identical-bodied twins could still fool git's own diff (which disambiguates by content-matching, the same fundamental approach our own hash-matching uses) -- would need its own "only trust the translated position if it resolves unambiguously, else stay honest" discipline, plus a dedicated test proving that discipline actually holds, to avoid a worse regression (confidently wrong instead of honestly incomplete). **Decision: not worth building.** The triggering condition (ALL structurally-identical siblings losing their unique anchor at once) is already rare; adding this much complexity for it, when the current behavior already degrades safely (reports the drift, points at nothing), isn't a good trade -- "better to point at nothing than risk pointing at the wrong place," the user's own words, and consistent with every other "never wrong, sometimes incomplete" decision already made in this project. Not pursued further.

**The practical resolution for a lingering, unmatchable warning already exists, no new feature needed**: manual testing surfaced a real, concrete instance of this edge case -- documenting one twin, then attempting to document the other, produced a QuickPick offering "Update documentation" instead of "Document selection" (because `findStaleRecordForSelection`'s selection-matching hit the exact same ambiguity), and accepting it overwrote the WRONG record, leaving one warning with no selection that `findStaleRecordForSelection` will ever match again -- so the editor context menu's "Update documentation" can never reach it (confirmed as the intended rule, not a bug: that action only appears when a selection can be matched to a stale record at all). But **Documented Sections' own Delete button already resolves this**: it's bound directly to the record's own ID from `findDocumentedNodes`, never routed through selection-matching, so it deletes correctly regardless of whether the editor context menu can find the record via the current selection. Confirmed both records still appear there with working Edit/Delete even in this exact tangled state.

## User-facing note: moving rapid-docs from the primary Activity Bar to the Secondary Side Bar

On first install, rapid-docs' views live under its own icon in the primary Activity Bar (left edge), same as any other extension. A user who wants it permanently visible alongside the editor (rather than switching to it) can move it to the Secondary Side Bar (the panel VSCode can show on the right edge) using entirely native VSCode window management -- nothing rapid-docs-specific to build or configure:

1. Right-click the rapid-docs icon in the (left) Activity Bar.
2. Choose **"Move View..."** from the context menu.
