# VSCode Extension Parity Checklist

**Method (agreed 2026-08-10, mandatory going forward):** go section by section, in real dependency order, bottom-up. A section is only marked CLOSED once every real capability in it is verified with real evidence (a proof file, a screenshot, an exact value checked against ground truth), never just "looks right" or "compiles." This includes things that don't show up as a UI click, like resource cleanup, not just visible features. Do not start the next section until the current one is CLOSED. `electron/` and `src/` are never edited for extension-specific reasons, only for genuine, general bug fixes (like the `decorators-legacy` parser fix below); they stay as the untouched reference to check every section against.

**Section order, and why:** (1) Extension lifecycle, since every later test depends on it running cleanly. (2) `AstService`, the deepest leaf dependency. (3) `GitService`, the other leaf, independent of `AstService`. (4) `DocumentationService`, built on `AstService`. (5) `SyncService`, built on `GitService` + `DocumentationService`. (6) `LiveWatchService`, built on `GitService` + `SyncService`. (7) UI layer, built only once 1-6 are fully proven, since Archive/the right-click menu/the compose Webview all depend on `DocumentationService` methods that weren't tested yet when those UI pieces were first touched. (8) A final explicit confirmation pass on everything deliberately not ported.

### Architecture audit and rebuild (2026-08-11)

After 7.4's first version shipped, real, repeated bugs surfaced (a right-click menu showing the wrong action for the current selection; diagnostic clicks silently failing) that no amount of incremental patching fixed. At the user's explicit direction ("audit how electron worked... replicate exactly, not patch and patch and patch"), every Section 7 piece was re-compared against the actual Electron mechanism it's supposed to replicate, not just its visual result. Findings:

- **7.2 Documented Sections — confirmed already correct, no rebuild.** Electron's row click (`renderer.js:789`) is bound directly to the `section` object already in memory via closure, no re-derivation. `documentedSectionsViewProvider.ts`'s rows do the exact same thing (`item.recordId` captured directly in the click handler, looked up from in-memory `this.items`). Structurally identical to Electron.
- **7.3 Compose's `activeEditorTracker` — confirmed a necessary platform adaptation, not a deviation.** Electron's compose button read Monaco's selection synchronously at click time, reliable because Monaco lived in the same process as the button. Our Compose panel is a genuinely separate VSCode `WebviewPanel`; `activeTextEditor` goes stale the instant it has focus. There is no synchronous equivalent to reach for here the way there was in Electron -- this is a real platform difference, not a shortcut.
- **7.4 context menu — confirmed broken by design, not just buggy.** It never replicated Electron's real mechanism (compute everything fresh, synchronously, BEFORE the menu is ever shown -- `renderer.js:334-395`). It used VSCode's declarative, pre-computed `when`-gated native menu instead, which requires keeping a context key updated reactively, ahead of time -- structurally race-prone against a fast select-then-right-click, and narrowing the update timing was never going to fully close it (VSCode's own `setContext` dispatch has latency outside our control).
- **7.1 Diagnostics click-to-highlight — confirmed broken by the same root cause.** Electron's Problems row click (`renderer.js:1064`) is ALSO bound directly to the message object via closure (`onRowClick(item, key)`), no lookup. VSCode's native Problems panel gives extensions no such hook -- clicking a row just navigates the editor, forcing `diagnosticClickHighlight.ts` to reverse-engineer which diagnostic was clicked by matching the resulting selection back against `vscode.languages.getDiagnostics()`. That indirection was the actual cause of the warning/info click flakiness, not fixable with better matching logic.

**Rebuild, both closing the same class of gap:**
- **7.4** rebuilt as one static `editor/context` menu entry (`rapidDocs.showEditorActions`, no context key, no `when` beyond `editorTextFocus`) that opens a `vscode.window.showQuickPick` built from `findRecordForSelection`/`findStaleRecordForSelection` computed fresh, synchronously, at the moment of invocation -- the direct VSCode equivalent of Electron's `showContextMenu`. `selectionContextKey.ts` (the old reactive approach) deleted.
- **7.1** rebuilt: `webviews/problems/problemsViewProvider.ts`, a real `WebviewView` whose rows carry the actual `RapidDocsMessage` object directly (matching Electron's closure-bound `onRowClick` exactly) -- clicking a row posts that same object back, never reconstructed from a VSCode navigation event. Includes the checkbox/Clear Selected/Clear All/per-row Delete (error severity only) interactivity native Diagnostics can't provide at all, closing 7.6's original gap too. The native `DiagnosticCollection` is kept, unchanged, purely for squiggly underlines and the native Problems tab's own click-to-navigate -- both still real, free, valuable VSCode integration. `diagnosticClickHighlight.ts` (the reconstruction-based approach) deleted.
- Compiled clean, activation smoke-tested (proof file, timestamp fresh). **Full interactive re-verification (clicking through the actual QuickPick and Problems webview) is still needed** -- this rebuild happened while the user was away and could only be confirmed statically; do not mark 7.1/7.4 CLOSED until that happens.

### Second rebuild: Problems goes native-only, plus real platform-constraint findings (2026-08-11)

Interactive re-verification of the rebuild above surfaced two more real, confirmed issues -- both root-caused with direct evidence, not patched blind:

- **`writeDoc`'s info message never clearing, root cause found**: `.rapid-docs/` was listed in THIS repo's own `.gitignore` (added for the tool's own dev-repo hygiene, not a general recommendation). `LiveWatchService.isIgnored()` (`live-watch.service.ts:91-96`) excludes every gitignored path from the chokidar watch entirely, so `.rapid-docs` was never watched at all -- meaning `deriveSourcePathFromStoragePath` (the mechanism that catches a storage-only mutation like `writeDoc` and rechecks the corresponding source file) could never fire. Confirmed live: documented a fresh function, the "no documentation yet" info message stayed in Problems even after a full window reload. Fixed by removing `.rapid-docs/` from this repo's `.gitignore`, matching how a real target repo is actually meant to be set up (`.rapid-docs` tracked and pushed, per the explicit "collaborator's `git pull`" comment already in `live-watch.service.ts`) -- confirmed working immediately after: the info message cleared correctly once `writeDoc` succeeded. **General lesson, not specific to this repo**: any target repo that gitignores `.rapid-docs` will hit this exact same gap, in Electron too (shared code) -- worth a real product decision later about whether `.rapid-docs` should ever be gitignorable at all.
- **Custom Problems webview's file-scoping bug, root cause found**: `problemsViewProvider.ts`'s `setActiveFile(null)` clears its list to empty (`postCurrentFileMessages`, `problemsViewProvider.ts:105-111`), and `extension.ts`'s `onActiveEditorChanged` was calling it from `vscode.window.activeTextEditor` directly rather than through the already-built `activeEditorTracker`. Opening Compose (a `WebviewPanel`) steals editor focus, `activeTextEditor` goes `undefined` (the same root cause documented above for 7.2/7.3), so the Problems webview wrongly cleared to empty -- even though nothing about the underlying messages had changed. Confirmed live: selected code, picked "Document Selection" (which only opens Compose, never writes anything), the info row vanished immediately; clicking back into the source file tab brought it back. First attempted a one-line fix (swap in `activeEditorTracker.getEditor()`), confirmed working, but then, per explicit user direction to prefer native mechanisms over custom ones once discussed, the whole custom Problems webview was removed instead of patched.
- **Decision (2026-08-11): Problems goes native-only.** `webviews/problems/problemsViewProvider.ts` deleted entirely, along with its `extension.ts` wiring, its `rapidDocsProblems` view contribution in `package.json`, and the now-dead `ProblemsMessagesSink`/`messagesByFile`/`replaceFileMessages` plumbing in `diagnosticsController.ts`. Native `DiagnosticCollection` (unchanged) plus `diagnosticPositionHighlight.ts` (cursor-position based, already native-first, needed no changes) are now the ONLY Problems mechanism. Clear Selected/Clear All confirmed not needed (messages naturally clear on their own once resolved); per-row Delete for fully-stale records lost its only implementation and now needs a native replacement -- see 7.6 below, this is the one real capability gap the removal opened up.
- **Native Problems panel has the exact same underlying root cause, on VSCode's own side.** Its built-in "Show Active File Only" filter (on by default, confirmed via its own filter-funnel menu) also reads the same stale `activeTextEditor` state -- so it too shows 0 while Compose has focus. Confirmed live. This is native, user-toggleable VSCode behavior (the user can turn the filter off themselves), not something in our code and not something to build a workaround for.
- **Developer quirk, re-confirmed via a second, different real trigger (2026-08-15): the same "Show Active File Only" staleness also shows up going Output panel -> Problems panel, not just Compose -> Problems.** Real, live-reported sequence: open Output (any channel, e.g. the new Activity log), switch to Problems, click a file tab that genuinely has diagnostics -- the list shows empty. Clicking a DIFFERENT file tab, then back to the original one, "catches it up" and it displays correctly from then on. Same root cause as above (the filter reads `activeTextEditor`, which is stale/undefined while a non-editor panel like Output has focus) via a different path to trigger it. **Confirmed there is no fix available from the extension side**: `diagnosticCollection.set()` is the only lever this (or any) extension has over native Problems, and it has zero visibility into or influence over when VSCode's own internal filter re-evaluates `activeTextEditor` and re-renders its tree -- that refresh timing is core VSCode UI plumbing, not exposed through any extension API. The only real remedies are both user-side, native settings, not code: turn "Show Active File Only" off entirely (Problems then always shows every file, all the time, nothing to go stale), or accept the occasional double-click-to-catch-up as expected, unfixable-by-us behavior.
- **Real, confirmed platform constraint: deselecting a highlight by re-clicking the same native Problems row does not work, and can't be made to.** Native Problems rows give extensions no click callback of their own (unlike the removed custom webview) -- only cursor-position changes via `onDidChangeTextEditorSelection` to react to, and VSCode does not fire that event when the selection doesn't actually change. Confirmed live with a two-diagnostic test: clicking a DIFFERENT row correctly moves the highlight (a real position change fires a real event); re-clicking the SAME row leaves the highlight untouched (no event fires at all, so `highlightController.toggle()` -- itself confirmed correct in isolation -- never runs a second time). The working deselect path: click anywhere else in the code outside any rapid-docs diagnostic range, which correctly clears the highlight via the existing `if (!match) { highlightController.clear(editor); return; }` branch.

## User-facing note: moving rapid-docs from the primary Activity Bar to the Secondary Side Bar

On first install, rapid-docs' views live under its own icon in the primary Activity Bar (left edge), same as any other extension. A user who wants it permanently visible alongside the editor (rather than switching to it) can move it to the Secondary Side Bar (the panel VSCode can show on the right edge) using entirely native VSCode window management -- nothing rapid-docs-specific to build or configure:

1. Right-click the rapid-docs icon in the (left) Activity Bar.
2. Choose **"Move View..."** from the context menu.
3. Pick **"Secondary Side Bar"** from the list that appears.
4. If the Secondary Side Bar isn't visible yet, toggle it on via **View > Appearance > Secondary Side Bar**, or `Ctrl+Alt+B`.

Dragging the icon directly onto the right edge of the window works too, once the Secondary Side Bar is visible. Either way moves the whole view group (Documented Sections, etc.), not just one panel. This is standard, native VSCode behavior available to any extension's views -- confirmed to work for rapid-docs the same as any other, nothing extra needed on our side.
